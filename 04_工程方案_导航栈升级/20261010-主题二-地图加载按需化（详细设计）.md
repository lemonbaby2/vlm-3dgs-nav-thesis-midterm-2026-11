## 1. 背景与现状（代码级）

### 1.1 现在的启动加载做了什么

`x_slam.cc:112-133` 在 localization 模式调 `load_map`（`laser_mapping.cc:12977` 起），流程：

1. 清场、读外参、中断事务恢复
2. 读 `poses_localization.txt` 全部位姿（`:13187-13212`）
3. **循环全量读所有关键帧 PCD**：`surf/<i>.pcd` + `ground/<i>.pcd` + `obs/<i>.pcd`（`:13225-13431`）
4. 建全局 IVox（全部 surf 变换插入，`:13483-13501`）
5. 建位姿 KD-Tree（`:13503+`）、重建 GTSAM 先验因子图（`:13503-13547`）
6. 拼 `localization_loaded_map_`（`:13616`）
7. 触发 `visualizeGlobalmap()` 发布显示

按 `x_slam_大地图加载耗时分析.md:52-61`，全图级扫描共 **4 次**：读 PCD → 全局 IVox → loaded_map → 显示拼接。其中第 3、4 次（Spec 待删）产出物一个没人用、一个前端只能整图收。

### 1.2 现在的显示链路

- `/x_nav/global_map`：以**最后一个关键帧**为中心、半径 600m 选关键帧 → 拼接 → 0.3m 降采样（`globalMapVisualization*` 参数）
- 前端（`web_app`，React + Three.js）通过 Foxglove WebSocket 收 `sensor_msgs/PointCloud2`，静态话题**累加约 100 帧**（`src/pages/index/index.tsx:171-172`），无分块、无 LOD
- 前端其实已声明分块接口与类型（`src/constants/api.ts:40`、`src/types/api.ts:24-47`），但后端/算法未实现；旧版本曾设计过 `chunks/index.txt`（`release_notes/2605/260520/commu.md:165-177`）

### 1.3 planner 侧（本轮只记录，不改）

planner 启动全量读 `global_map.pcd` 建 KD-Tree/体素图/SDF/拓扑（`x_planner.cpp:5712/5728`），属主题六，本主题只负责为它产出可分块的数据基础。

### 1.4 两个已存在的"局部化"机制（改造的基础）

- 运行期 `recontructIKdTree_now(center)`（`:7943`）已经会按当前位置选附近关键帧拼局部子图、重建**局部 IVox**
- 定位初始化的多候选 GICP：以初始位姿为圆心、半径 4m（`localization_search_radius`）搜邻近关键帧拼局部地图

也就是说"按需"的运行期机制本该存在，缺的是**把它提前到启动/加载阶段**，并让**关键帧 PCD 不必全部进内存**。

## 2. 目标与不变量

### 2.1 目标

1. 启动只读位姿与索引（K 级，百 KB~MB 级），**不读关键帧 PCD、不建全局 IVox、不拼 loaded_map**
2. 点云按需读取：按当前位置选关键帧 → 读 PCD → 局部子图 → 局部 IVox；LRU 缓存 + 预取
3. 显示与匹配解耦：显示用分块 LOD 产物；匹配用按需局部子图
4. 前端首屏只拉当前视口/当前层瓦片，可缓存、可版本失效
5. 旧地图可离线补齐新产物；缺产物时优雅回退到旧全量路径

### 2.2 不变量（评审重点）

- **话题语义不变**：不改 `/x_nav/global_map`、`/x_nav/current_pointcloud*`、`/base_link/odom`、`/x_nav/local_map` 的对外行为（Spec 删除 loaded_map 的话题静默属已确认变更）
- **产物向后兼容**：关键帧文件格式不动；新增产物只做扩展
- **回退开关**：`on_demand_load_enable=false` 时恢复旧全量加载
- **显示不依赖内存关键帧容器**：全图预览来自 LOD 产物
- **内存有上限**：关键帧缓存 + 局部 IVox 合计不超过预算

## 3. 概念速览（正文用到的角色）

> 详细解释见附录 A。这里先建立一句话印象。

| 概念 | 一句话 |
|---|---|
| 关键帧 | 建图时每隔一段路保存的一帧点云 + 位姿，是地图的最小单位 |
| 位姿 KD-Tree | 按 x/y/z 快速找"附近有哪些关键帧"的通讯录 |
| IVox | 体素哈希近邻索引，匹配时"就近找点"的快递柜 |
| 全局 IVox / 局部 IVox | 给整张图铺柜子（要删）/ 只铺当前位置附近（保留） |
| loaded_map | 启动时把全图拼一份的内存副本（没人用，要删） |
| chunk（分块） | 把大图按空间切成格子，按格加载/显示 |
| buffer_width | 分块查询时的"光晕"宽度，避免边界漏帧 |
| LOD / 瓦片 | 多分辨率（近高清远低清）与按格取图 |
| LRU 缓存 | 装不下的缓存就淘汰"最久没用"的 |
| 预取 | 提前读"马上要用"的块 |
| Foxglove WS | 实时话题的 WebSocket 通道（动态数据） |
| HTTP 瓦片 | 静态地图文件的 HTTP 下载（可缓存、可版本号） |

## 5. 设计 B：关键帧按需读取（IO/内存侧瘦身）

### 5.1 启动最小加载集

启动只读这些小文件（均与地图规模**弱相关**）：

| 文件 | cf09301 实测 | 用途 |
|---|---|---|
| `keyframe_index.json` | 73.5KB | 关键帧位姿（6DoF）+ global/local id + 文件路径 + overlap |
| `poses_localization.txt` | 14KB | 兼容旧路径（与索引二选一或交叉校验） |
| `chunks/index.json` | 预计几 KB | 分块索引（本主题新增，见设计 C） |
| `ground_levels.json/txt`、`stairs/*`、`nav_points.txt` | 小 | 楼层/语义/航点 |

不读任何 `surf/ground/obs/*.pcd`。位姿 KD-Tree 由 `keyframe_index.json` 的 `pose_global` 构建。

### 5.2 运行期读取链路

```
初始位姿/重定位候选（人工、GPS、或主题五 L1/L2）
  → 位姿 KD-Tree 半径搜索（localization_search_radius，默认 4m）
  → 得到邻近关键帧集合 [i1..ik]
  → KeyframeCache.GetSurf(i)（命中内存 → 否则读盘 surf/<i>.pcd）
  → 变换拼接 → 局部子图（降采样）→ GICP 定位
  → handoff：recontructIKdTree_now(位姿) → 局部 IVox
跟踪中：
  每帧 MapIncremental 在线加点（不变）
  滑动窗口吸收新关键帧 + removeFarPoints（设计 A）
  关键帧缓存按位置淘汰/预取
```

### 5.3 KeyframeCache（关键帧缓存）

- 键：`(map_id, keyframe_id)`；值：`surf/ground/obs` 点云 shared_ptr（ground/obs 可选，仅显示/保存路径需要）
- 容量：`on_demand_cache_mb`（建议 1024MB，待定）；LRU 淘汰
- 与主题一的 Provider **共用同一实现**（主题一叫 `KeyframeCloudProvider`，本主题只是全量场景下的同一组件）
- 线程安全：`mtx` + 缓存互斥；读盘在调用线程同步执行（首版），实测不足再异步化

### 5.4 预取策略

- 方向预取：按机器人速度方向，取"前方 1~2 个 chunk"里的关键帧预热
- 时间预取：当前 chunk 内下一批索引
- 边界预取：跨 chunk 前预取 `buffer_width` 内的邻块（避免跨格帧）
- 预取线程优先级低于定位链路；失败不阻塞主链路

### 5.5 降级与失败处理

| 场景 | 行为 |
|---|---|
| `chunks/index.json` 缺失 | 回退旧全量加载（开关 + 告警），或离线补生成 |
| 单帧 PCD 读失败 | 告警 + 跳过该帧；子图点数不足时扩大半径补帧 |
| 磁盘 IO 超时 | 使用现有局部 IVox 兜底（跟踪不停），后台重试 |
| 缓存打满 | 优先淘汰"距离远 + 非预取"的条目；必要时降低预取并发 |

### 5.6 与设计 A 的关系

- A 解决"匹配索引不建全局"；B 解决"关键帧点云不读全量"。两者独立可分别上线；合起来才是完整的启动瘦身
- 首次定位所需的"附近关键帧"来源从内存容器改为 Cache，语义不变

## 6. 设计 C：分块与 LOD 产物

> **瓦片产物的完整规范（目录/命名/字段字典/文件格式/版本/边界）统一见附录 D**——本附录是"瓦片"的规范唯一出处，本节只保留设计要点；生成（finalize/CLI）见主题一 §4.14，前端消费见 §7，planner 区域加载见主题六 §5.3。

### 6.1 chunk 定义（复用旧协议）

- **网格**：2D 方格，`grid_x = floor(pose.x / chunk_size)`，`grid_y = floor(pose.y / chunk_size)`
- **归属**：按**关键帧位姿**入格（一个关键帧只属于一个 chunk，永不拆帧）
- **参数**：`chunk_size` 起步 20~50m（待定，建议 30m）；`buffer_width` 5~10m（查询光晕，只影响读取范围，不重复存点）
- **多楼层**：网格只在 x/y 分块；chunk 元数据带 `z_range` 与 `floors`（楼层号集合）
- **物理存储不动**：`surf/ground/obs/<i>.pcd` 保持现状；chunk 是**索引 + 显示产物**

### 6.2 产物格式（建议）

目录：

```
<map>/
  chunks/index.json                ← 分块清单（前端 MapChunkData 对齐）
  chunks/<gx>_<gy>/lod1.pcd        ← 该块 0.2~0.3m 降采样（中距显示）
  chunks/<gx>_<gy>/lod0.pcd        ← （可选，P3）该块全精度拼接（近距显示）
```

`chunks/index.json` schema（建议）：

```json
{
  "version": 1,
  "map_id": "cf09301",
  "chunk_size": 30.0,
  "buffer_width": 5.0,
  "cache_radius": 60.0,
  "source_pose_version": 1,
  "generated_at": "2026-10-10T15:00:00",
  "total_chunks": 4,
  "total_keyframes": 170,
  "chunks": [
    {
      "grid_x": 0, "grid_y": -1,
      "bbox": {"min_x": -5.0, "min_y": -30.0, "max_x": 25.0, "max_y": 0.0},
      "z_range": [-0.73, 4.07],
      "floors": [0],
      "keyframes": [0, 1, 2, "..."],
      "keyframe_count": 42,
      "patch_ids": ["floor_0", "stair_A_t01"],
      "fragments": "chunks/0_-1/fragments.json",
      "dirty": false,
      "lod1": "chunks/0_-1/lod1.pcd",
      "lod0": "chunks/0_-1/lod0.pcd"
    }
  ]
}
```

- `source_pose_version` 与 `keyframe_index.json` 的 `pose_version` 联动：闭环/合并/编辑后版本 +1 → 前端缓存失效、瓦片由烘焙/CLI 重算
- 与前端已声明类型对齐：`MapChunkData`（`web_app/src/types/api.ts:24-47`）字段一一对应，补 `z_range/floors/patch_ids/dirty/lod1` 扩展
- `patch_ids / fragments`：**瓦片与语义的挂接**（主题一 §4.14）——加载某块即知其属于哪些楼层/面片；点楼梯可高亮跨块；planner 可做语义感知预取
- `dirty`：保留字段，用于"版本落后/待重烘焙"的显式标记；前端遇到 `dirty=true` 或版本不一致则忽略缓存
- **生成时机**：**finalize 烘焙（主路径）+ 旧图 `semantic_tool tile` 补算**；合并/编辑后由统一重烘焙流水线重算（主题一 §4.14、主题三 §4.3）

### 6.3 LOD 约定（避免与"楼层 level"混淆）

> 本方案中 **LOD** 指分辨率层级；**floor/level** 指楼层。命名上建议产物用 `lodN`，楼层用 `floor_id`。

| LOD | 数据源 | 体素 | 用途 | 加载策略 |
|---|---|---|---|---|
| L2 | `global_map_downsize.pcd`（已有） | 0.3m | 全图预览/远景/小地图 | 启动可选加载（几百 KB） |
| L1 | `chunks/<gx>_<gy>/lod1.pcd`（新增） | 0.2~0.3m | 中距区域显示 | 视口内按需 |
| L0 | `chunks/<gx>_<gy>/lod0.pcd`（可选） | 原精度 | 近距高清显示 | 近距按需（P3） |
| 匹配 | `surf/<i>.pcd` | 原精度 | GICP/IVox 局部匹配 | 运行期按需（设计 B） |

- L0 是否落盘：可以直接流式读关键帧 PCD 拼（复用 Cache），省磁盘；P3 再决定
- 楼层过滤（主题四）在任一 LOD 上叠加：用 chunk 的 `floors/z_range` 或 levels 产物

### 6.4 生成方式

1. **finalize 烘焙（主路径，C++）**：地图保存时从磁盘流式切块 + 降采样，产出 `chunks/` 与 `index.json`（主题一 §4.14）；finalize 校验"索引覆盖全部关键帧、版本与 `keyframe_index` 一致"
2. **旧图补算 / 重烘焙（兼容路径）**：C++ CLI `semantic_tool tile --map-dir ...`（Python 工具仅保留地图检查/合并类运维功能）
3. **合并/编辑后**：统一重烘焙流水线重算（主题三 §4.3）
4. **不做在线切割**：瓦片是加载侧产物，建图过程不需要它；实测 finalize 全量烘焙仅 0.68s（主题一 §11.3 A4），无需为它引入常驻累加器/批写/在线脏块管理

> 与"全局粗图（nav_light）"的区别：瓦片 LOD 是**给前端/局部执行看的高清点云块**；nav_light 是**给全局规划看的低清栅格**（1 字节/格，主题一 §4.15 / 主题六）。两者同版本、不同用途，不要混用。

### 6.5 失效与兼容

- 版本号：`source_pose_version` 不一致 → 消费者忽略缓存并请求最新；由产物烘焙/CLI 重算
- 旧地图：无 `chunks/` → 运行时回退全量；`semantic_tool tile` 补算后可切换到按需
- 合并/裁剪后（主题三）：触发**统一重烘焙流水线**（瓦片/粗图/语义一并重算，走主题一 CLI 形态），不再各处各自重生成

## 7. 设计 D：前端数据通道与渲染

### 7.1 静态/动态分层

| 层 | 数据 | 通道 | 特性 |
|---|---|---|---|
| 静态底图 | L2 全图 downsize、L1/L0 分块瓦片、关键帧位姿（可选） | **HTTP**（静态文件/服务） | 可缓存、可版本号、断线可恢复 |
| 动态数据 | `current_pointcloud`、障碍、导航点、机器人位姿 | **Foxglove WS**（现状） | 实时、增量 |
| 控制 | 地图切换、保存、重定位命令 | 现有 HTTP API | 不变 |

**移除**前端对 `/x_nav/global_map` 整图的展示依赖与累加逻辑（`index.tsx:171-172`）；`/x_nav/global_map` 保留给 RViz/兼容消费者。

### 7.2 后端接口（建议）

| 接口 | 返回 | 说明 |
|---|---|---|

| `GET /api/extra/get_levels?map=<name>` | `levels/index.json`（主题四） | 楼层切换（预留） |

### 7.3 TileManager（前端核心组件）

```
状态：camera 视口 + 机器人位置 + 当前楼层
每帧（节流 ~10Hz）：
  1. 计算可见 chunk 集合（视锥/半径）
  2. 按"距离 + 朝视中心"排序，选择 LOD：
       近（< R1）→ L1（或 L0）
       中（R1~R2）→ L1
       远 → L2 全图
  3. 对每个未加载 chunk 发请求（并发上限 N=4~6）
  4. 移出视野/低优先级请求 AbortController 取消
  5. 解析放 Web Worker（Transferable ArrayBuffer），主线程只建 BufferGeometry
  6. LRU：超内存预算（按点数/MB）淘汰最远/最久未用
  7. 渐进式：先 L2 占位，L1/L0 到达后替换
```

### 7.4 渲染优化

- 每个 chunk 一个 `THREE.Points`（或合并少量块），共享材质；颜色按强度/高度可切换
- 视锥剔除（Three.js 自带）+ 距离淡出
- 点大小按 LOD 调整；避免频繁重建 BufferGeometry（对象池）
- 与主题四图层系统（关键帧/patch/楼层）共用渲染管线与拾取（Raycaster）

### 7.5 迁移步骤（前端）

1. 保留现有实时层渲染；新增 TileManager 只负责静态底图
2. 默认关：`use_tile_basemap=false` 时行为与现状一致
3. 打开后逐步移除累加逻辑；旧 `global_map` 订阅退订
4. 性能验收后默认开启

## 附录 A：专业名词详解

> 按"是什么 → 为什么需要 → 在本方案中的角色"三段式，尽量用大白话。

### A1. 关键帧（Keyframe）
- **是什么**：建图时机器人每隔一小段路（或满足条件时）保存的一帧点云 + 该时刻位姿。地图由很多关键帧拼成。
- **为什么**：连续每帧都存太大；隔一段存一帧，既能还原地图又能控制体量。
- **本方案角色**：最小存储/加载单位；按需加载就是"按关键帧加载"。cf09301 有 170 帧。

### A2. 位姿（Pose）
- **是什么**：机器人在某一刻的位置（x, y, z）和朝向（roll, pitch, yaw 或四元数），共 6 个自由度（6DoF）。
- **为什么**：点云只记录了"相对机器人的形状"，必须靠位姿把它摆到地图里的正确位置。
- **本方案角色**：启动只读位姿（很小），所有"找附近关键帧"靠位姿做索引。

### A3. 位姿 KD-Tree
- **是什么**：一种空间二分查找树。把每个关键帧的 (x, y, z) 挂到树上，查询"以某点为中心半径 R 内有哪些关键帧"非常快。
- **为什么**：顺序遍历几千个位姿也能做，但 KD-Tree 在 K 大时更省时间；K 本身很小，构建也快。
- **本方案角色**：启动阶段的核心索引；只依赖位姿文件，不依赖点云。

### A4. IVox（增量体素哈希地图）
- **是什么**：把空间切成固定边长的小立方体（体素），点按所在格子存进哈希表；查询时只翻"附近 3×3×3 个格子"。像按柜号存取的快递柜。
- **为什么**：实时匹配（GICP/最近邻）需要毫秒级"就近找点"，全图遍历太慢。
- **本方案角色**：匹配索引。容量有上限（40000 体素 LRU + 50 点/体素），所以内存本身有界。

### A5. 全局 IVox vs 局部 IVox
- **全局 IVox**：启动时把所有关键帧的点都塞进一个 IVox，铺满整图。**本方案要删**——因为定位一开始就会用"局部 IVox"替换它，它其实没被用过。
- **局部 IVox**：只把机器人当前位置附近的关键帧点云塞进去，随位置滚动更新。**保留并强化**（滑动窗口）。

### A6. 局部子图（Submap）
- **是什么**：从地图里挑"当前位置附近的一批关键帧"，拼成一张小地图。
- **为什么**：匹配只需要近处高精度环境，不需要整图；小图又快又稳。
- **本方案角色**：按需加载的直接产物：选帧 → 读 PCD → 拼接降采样 → 交给 GICP。

### A7. GICP（广义 ICP）
- **是什么**：一种点云配准算法。把当前激光帧和子图"对齐"，求出机器人最可能的位姿。ICP 系列是"局部优化"：初值必须足够近。
- **为什么**：这是定位/跟踪的核心计算。
- **本方案角色**：不改变；只是它的"目标子图"从内存全量改为按需加载。

### A8. PCD 文件
- **是什么**：点云的标准文件格式（PCL 的 Point Cloud Data），本系统用二进制存 `surf/ground/obs/<i>.pcd`。
- **为什么**：每帧一个文件，便于单帧原子写、按需读、增量维护。
- **本方案角色**：按需读取的最小单位；瓦片（LOD）也是 PCD 文件。

### A9. loaded_map（`localization_loaded_map_`）
- **是什么**：启动定位模式时，把**所有**关键帧点云变换到全局坐标拼成的一张大点云，常驻内存。
- **为什么存在**：历史实现给 `/x_nav/local_map` 话题当发布缓存。
- **为什么删**：所有算法链路都不读它；唯一消费者是那个话题（已确认零影响）。删掉省一次全图拼接 + 常驻内存。

### A10. chunk（分块）
- **是什么**：把平面按方格切成很多格（例如每格 30m×30m），关键帧按所在格归属；加载/显示/传输都以格为单位。
- **为什么**：让"整图"变成"一小块一小块"，实现按需与并行。
- **本方案角色**：核心组织单位；`chunks/index.json` 记录每格有哪些关键帧、范围多大、LOD 文件在哪。

### A11. buffer_width（缓冲/光晕宽度）
- **是什么**：查询时在格子边界外多读一圈的宽度（如 5~10m）。
- **为什么**：机器人站在格子边界时，只读本格会缺邻格的点，匹配/显示出现"缺口"。光晕只是读取范围，不重复存储。
- **本方案角色**：防边界漏帧的关键参数。

### A12. cache_radius（缓存半径）
- **是什么**：以机器人为中心，缓存/预取多大范围内的块。
- **为什么**：走远了旧块要淘汰、新块要提前读——半径决定缓存的工作集大小与预取范围。
- **本方案角色**：LRU 失效与预取的判定依据之一。

### A13. LOD（Level of Detail，多分辨率）
- **是什么**：同一区域准备多个精细度的版本：近处高清（点密）、远处低清（点稀）。
- **为什么**：屏幕就那么大，远处给全精度是浪费；低清版能显著省带宽/内存/GPU。
- **本方案角色**：L2=全图 0.3m 降采样（已有）；L1=每块 0.2~0.3m；L0=近距原精度（可选）。
- **注意**：和"楼层 level"是两码事，命名建议区分（`lodN` vs `floor_id`）。

### A14. 瓦片（Tile）
- **是什么**：按网格切好的一个个地图文件，前端"看哪拉哪"。
- **为什么**：类似地图 App：不下载整张地图，只拉当前视野的瓦片，滚到哪拉到哪。
- **本方案角色**：静态底图的传输单位；URL 形如 `/tiles/<map>/<gx>_<gy>/lod1.pcd?v=版本号`。

### A15. 体素降采样（Voxel Downsample）
- **是什么**：把空间切成小立方体，每个立方体里的多个点合并成一个代表点（或取平均）。点数变少、形状保留。
- **为什么**：原始点云太密；显示和规划不需要那么密。
- **本方案角色**：生成的 LOD/瓦片都用它；0.3m 是现有默认。

### A16. LRU（最近最少使用缓存）
- **是什么**：缓存满了就把"最久没被用到"的东西扔掉，给新东西腾地方。
- **为什么**：内存有限；机器人一般只在某片区域活动，"久未用"= 大概率短期也用不到。
- **本方案角色**：关键帧缓存、前端瓦片缓存都用它管理。

### A17. 预取（Prefetch）
- **是什么**：还没用到就先把大概率马上要用的数据读进来。
- **为什么**：等到用时才读会有卡顿；提前读能把 IO 隐藏在后台。
- **本方案角色**：沿机器人前进方向预读 1~2 个 chunk 与邻格光晕。

### A18. Foxglove WebSocket
- **是什么**：一套在浏览器和机器人之间传 ROS 消息的实时 WebSocket 协议；点云以二进制消息推送。
- **为什么现在用它**：实时话题（当前帧点云、障碍、位姿）适合"推"模式。
- **为什么静态图改走 HTTP**：静态地图不需要每帧推送；HTTP 有缓存、断点、版本机制，且不占 ROS 图/带宽。
- **本方案角色**：动态数据保持 WS；静态底图改为 HTTP 瓦片。

### A19. PointCloud2
- **是什么**：ROS 的点云标准消息类型，含字段布局（x/y/z/intensity 等）与二进制数据。
- **本方案角色**：`/x_nav/global_map` 等话题仍用它；前端解析逻辑已有（`services/ros/pointcloud.ts`）。

### A20. 视锥（Frustum）与视锥剔除
- **是什么**：相机的可见范围像一个金字塔（视锥）。视锥剔除 = 不渲染明显看不到的物体。
- **为什么**：省 GPU；只画视野内的瓦片/点云。
- **本方案角色**：TileManager 选块的依据（视锥 + 距离）。

### A21. Web Worker 与 Transferable
- **是什么**：浏览器里跑在后台线程的脚本；Transferable 指把大块二进制内存"零拷贝"转交给其它线程。
- **为什么**：解析几 MB 点云放主线程会卡 UI；放到 Worker 里，主线程只负责画。
- **本方案角色**：瓦片解码/转 BufferGeometry 前处理在 Worker 完成。

### A22. AbortController
- **是什么**：浏览器提供的"取消请求"工具。
- **为什么**：机器人快速移动时，之前请求的瓦片可能已经移出视野；取消它们防止带宽和内存浪费。
- **本方案角色**：TileManager 的请求生命周期管理。

### A23. 渐进式渲染
- **是什么**：先用低清数据快速占位，高清数据到达后再替换。
- **为什么**：用户先看到"地图轮廓"比盯着空白舒服，也不影响自动导航。
- **本方案角色**：先 L2 全图/低清块，随后 L1/L0 替换。

### A24. 版本号与缓存失效
- **是什么**：给产物打一个"内容版本"（如 `source_pose_version`）。内容变了版本变，客户端据此知道旧缓存作废。
- **为什么**：闭环优化、地图合并、手工编辑都会让旧瓦片"位姿过时"，必须有机制让前端刷新。
- **本方案角色**：`chunks/index.json` 与瓦片 URL 的 `v=` 参数。

### A25. 降级/回退（Fallback）
- **是什么**：新机制不可用时，自动走旧机制，保证功能不丢。
- **本方案角色**：无 `chunks/` 的地图走全量加载；IO 超时用已有局部 IVox 兜底；开关关闭=现状。

| `buffer_width` | float | m | 查询光晕宽度（只影响读取范围） | 起步 5 |
| `cache_radius` | float | m | 预取/缓存半径 | 起步 60 |
| `source_pose_version` | int | — | 对应 `keyframe_index.json` 的 `pose_version` | 失效校验锚点 |
| `generated_at` | string | ISO | 生成/更新时间 | 运维 |
| `total_chunks` | int | — | 瓦片总数 | |
| `total_keyframes` | int | — | 覆盖关键帧总数（应等于索引总数） | 校验 |

**每块字段**（`chunks[]` 数组元素）：

| 字段 | 类型 | 单位 | 含义 | 备注 |
|---|---|---|---|---|
| `grid_x` / `grid_y` | int | 格 | 网格坐标 | 与目录名一致 |
| `bbox` | object | m | `min_x/min_y/max_x/max_y` 实际点云范围 | 可小于格子范围 |
| `z_range` | [float,float] | m | 高度范围 | 多层混块时用于分层 |
| `floors` | int[] | — | 涉及楼层（`ground_levels.level_id`） | 主题四按层过滤 |
| `keyframes` | int[] | — | 块内关键帧编号（local id） | 按需读原始帧 |
| `keyframe_count` | int | — | 帧数 | 校验 |
| `patch_ids` | string[] | — | 语义挂接：块内涉及的 patch | 主题一 §4.14 / 主题六 |
| `fragments` | string? | — | 切片索引路径（相对地图目录） | 可选；缺省=查询式现算 |
| `dirty` | bool | — | 版本落后/待重烘焙标记 | 前端遇 true 弃缓存 |
| `lod1` | string | — | lod1 路径（相对地图目录） | 必需 |
| `lod0` | string? | — | lod0 路径 | 可选 |

> 与前端已声明类型 `MapChunkData`（`web_app/src/types/api.ts:24-47`）对齐：`grid_x/grid_y/min_x/min_y/max_x/max_y/keyframes/keyframe_count` 一一对应；`id/z_range/floors/patch_ids/dirty/lod1/lod0` 为扩展字段（旧解析器忽略未知字段）。

### D.3 瓦片点云文件约定

| 项 | 约定 |
|---|---|
| 格式 | 二进制 PCD，字段 `x/y/z/intensity`（PCL `PointXYZI`） |
| `lod1` | 0.2~0.3m 体素降采样（默认 0.3m，参数 `tile_lod1_leaf`） |
| `lod0` | 原精度拼接（可选，P4；不落盘时由消费者流式读关键帧拼） |
| 归属 | 按**关键帧位姿**入格（不拆帧）；点云可略超格子边界，读取时结合 `buffer_width` 邻块 |
| 坐标系 | map 系（与 `global_map.pcd` 一致，可直接显示/规划） |

### D.4 版本与失效（摘要）

- 所有瓦片与 `source_pose_version` 绑定：版本不一致 → 消费者忽略缓存并请求最新
- 地图变化（合并/编辑/重建）→ 版本 +1 → 由**产物烘焙（finalize）或统一重烘焙流水线（CLI）**重算（主题一 §4.14、主题三 §4.3）
- 旧图无瓦片 → 运行时回退全量加载；`semantic_tool tile`（C++ CLI）补算

### D.5 与相邻产物的边界

| 产物 | 是什么 | 与瓦片的关系 |
|---|---|---|
| `levels/`（主题四） | 按楼层切的预览点云 | 瓦片管"空间块"，levels 管"楼层"；前端组合出"按层按块" |
| `nav_light/`（主题六） | 每层粗栅格（1 字节/格） | **给全局规划看的低清图**；瓦片是**给局部执行/显示看的高清块**——同版本、不同用途，勿混用 |
| `patch`（语义主表） | 可行走面片元数据 | 瓦片通过 `patch_ids/fragments` 挂接；语义永远认 patch 本体 |

### D.6 生命周期（谁写谁读摘要）

| 环节 | 动作 |
|---|---|
| 建图中 | **不生成瓦片**；关键帧正常落盘（瓦片是加载侧产物，建图不需要） |
| finalize | 从磁盘流式切块 + 降采样 + 写 `index.json`；校验完整性与版本 |
| 旧图/重烘焙 | `semantic_tool tile`（C++ CLI） |
| 前端 | HTTP 静态服务按 `?v=版本` 取瓦片；TileManager 视口加载（§7） |
| planner | 区域加载器沿走廊预取 `lod1`，建区域 Vox/SDF（主题六 §5.3） |
