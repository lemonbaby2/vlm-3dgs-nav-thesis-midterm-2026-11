### 1.2 缺口清单（本主题要解决的）

| # | 缺口 | 证据/影响 |
|---|---|---|
| 1 | 合并缺语义锚点：纯 ICP 在平坦/单层区域 **z 不可观**、相似走廊 yaw 有歧义 | `map_tool.py:930-945` 只做 ground/map 点云 ICP |
| 2 | 跨图语义 ID 不统一：两图都可能有 `stair_A`，无法表达"这是同一部楼梯" | `patch_id`/`stair_id` 仅图内唯一 |
| 3 | 合并产物不完整：`stairs/` 冲突只告警保留 A（`map_tool.py:1028-1035`）；`ground_levels` 不重生成；`id_allocator.json` 不更新 | 合并后跨层/楼层过滤可能失效 |
| 4 | 只能两两合并（pairwise），无 N 图链式/全局优化 | `merge --map-a --map-b` |
| 5 | 无在线续建：`load_map` 后只能定位，无"定位成功→继续建图→追加保存" | 模式初始化路径缺失 |

| 7 | 运行期跨图回环只在**建图模式且目标图目录存在于 nav_root** 时工作；定位模式/离线图之间无对齐通道 | `TryWriteInterMapOverlapFromLoop` 由建图 loop 线程调用 |

## 2. 目标与不变量

### 2.1 目标

1. **离线合并增强**：关键帧 ICP 为主 + patch 语义锚点（z/yaw）为辅；合并产物完整（索引/楼层/楼梯/分块/分配器）
2. **跨图语义关系**：全局语义 ID + 关系落盘；供合并、planner、前端消费
3. **在线续建（二期）**：打开已有地图 → 自动/人工定位 → 追加建图 → 保存续接，全程与主题一存储底座合流
4. **可视化工具**：关键帧位姿图层 + 合并质量报告，让对齐"看得见、可验收"

### 2.2 不变量

- 现有 `map_id` / `global_keyframe_id` / `overlap_to` / `keyframe_index.json` schema **只扩展不破坏**
- 旧地图无需迁移即可被现有流程使用；新能力缺失时优雅降级
- 合并工具**不修改输入图**，只产出新图（现有行为）
- 续建模式必须可回退到"独立新图 + 离线合并"路线

## 3. 概念速览（正文用到的角色）

| 概念 | 一句话 |
|---|---|
| map_id | 一张图的目录名（图级身份） |
| global_keyframe_id | 跨所有图唯一的帧号（id_allocator 分配） |
| overlap_to | 索引里记录的"本帧与别图某帧重叠"关系（含相对位姿/质量） |
| 跨图回环 | 机器人/算法发现两图看到同一处，用 ICP 求相对位姿并用 GTSAM 约束 |
| seed / anchor | 合并粗对齐的两种输入：直接给位姿（seed）或指定一对同物点帧（anchor） |
| patch | 楼梯/楼层面片（floor/tread/entry/exit），有编号、范围、高度 |
| floor mean_z | 楼层平面平均高度——合并的"z 锚点" |
| stair 轴向 | entry→exit 方向——合并的"yaw 锚点" |
| pose graph / GTSAM | 把位姿当节点、约束当边的图优化（闭环/多图约束都进这里） |
| fitness score | ICP 匹配好坏的分数（越小越好，用于质量评估） |
| 续建（session continue） | 打开已有图继续建，而不是从零建 |

## 4. 设计 A：离线合并增强（map_tool merge v2）

### 4.1 对齐流水线（粗 → 精 → 评）

```
输入：图A、图B（均有关键帧 + keyframe_index + [可选]patch/levels）
① 粗对齐（三选一，优先级从高到低）：
   a. --seed "x y z yaw"            已知相对位姿（人工测量/历史记录）
   b. --patch-anchor                语义锚点（本设计新增，见 4.2）
   c. --a-anchor i --b-anchor j     指定同物点关键帧对（现有）
② 精配准：
   地面/全图 ICP（--icp --align-cloud ground|map，现有）
   → 输出 T_AB（B 到 A 的 4x4 变换）
③ 质量评估（本设计新增，见 4.4）：
   重叠区 fitness、层高一致性、重影指标 → 报告 + 阈值判定
④ 落盘：现有搬运逻辑 + 产物补全（4.3）
```

### 4.2 patch 语义锚点（新增）

**输入**：两图都有合格 patch（`reviewed=true` 且未被归档）时启用；任一缺失则自动跳过（降级到现有方式）。

| 锚点 | 数据 | 算法 | 备注 |
|---|---|---|---|
| **z 锚点** | floor patch `mean_z`（如 A: floor_0 2.851 / B: floor_N 2.381） | 匹配楼层对（见下）→ `Δz = mean_z_B − mean_z_A`；seed 的 z 用它覆盖/校正 | 楼层匹配：优先用 `stair_graph` 的 from/to 对应；否则用重叠关键帧 z 最近匹配 |
| **yaw 锚点** | stair `entry→exit` 方向向量 | 两图同一楼梯方向差角 `Δyaw`；无 stair 时退化用 floor bbox 主轴或重叠区地面配准初值 | 轴向只在楼梯被正确复核时可靠 |
| **楼层对匹配** | `floor_id` + `stair_id` 邻接 | 若 A、B 共用同一 stair 语义对（entry 所在层/exit 所在层），直接建立 floor 对应 | 多楼层大图优先建立"楼层对应表" |

**参数**：`--patch-anchor [--floor-pair a:b] [--stair-pair A:stair_A,B:stair_B]`，默认自动推断，冲突时报错让人工指定。

**降级**：patch 缺失/被拒 → 打印明确告警，回落到 anchor/ICP；**绝不因 patch 缺失而失败**（cf09301 当前就是这种状态）。

### 4.3 合并产物补全（修复缺口 #3）

在现有 `merge` 输出基础上新增：

1. **`ground_levels.json/txt` 重生成**：用合并后 `global_ground_map.pcd` 重新聚类楼层；若两图 patch 有对应关系，按 patch `mean_z` 校验/修正（`fix_mapid.sh` 式后处理顺带修 `map_id`）
2. **`stairs/` 合并**：
   - 两图都有 stairs：默认告警保留 A（现状）；新增 `--stairs-policy`：`keep-a | keep-b | merge`（merge 时要求语义 ID 已全局化，见设计 B，否则只允许单边）
   - 语义 ID 冲突（两边都叫 stair_A 但实际是不同楼梯）→ 阻断 merge 并提示
3. **`global_index/id_allocator.json` 同步**：合并写入新 global id 后，推进分配器 `next_global_keyframe_id`（修复缺口 #3 的隐性坑：否则后续建图会撞号）
4. **统一重烘焙**（瓦片/粗图/语义一并重算，走主题一 CLI 形态）：合并改变了 bbox/覆盖与位姿，旧的 `chunks/`、`nav_light/`、在线语义草稿全部作废 → 触发一次统一重烘焙流水线（`semantic_tool tile / bake-nav / rebake`），不再逐项各自生成
5. **`levels/` 产物重生成**（主题四）：合并后楼层范围变化（在同一重烘焙流水线内完成）

### 4.4 质量评估与报告（新增）

合并后输出 `merge_report.json`（可与 validate 集成）：

```json
{
  "map_a": "cf09301", "map_b": "cf09281658", "out": "merged_cf",
  "transform": {"x":..., "y":..., "z":..., "yaw":...},
  "alignment": {"source": "patch-anchor+icp", "icp_fitness": 0.032, "iterations": 28},
  "anchors": {
    "floor_pairs": [["floor_0","floor_0"], ["floor_1","floor_1"]],
    "stair_pairs": [["stair_A","stair_A"]],
    "z_correction": -0.47, "yaw_correction_deg": 1.8
  },
  "quality": {
    "overlap_keyframe_pairs": 23,
    "overlap_fitness_mean": 0.028,
    "floor_height_consistency_m": 0.03,
    "ghosting_p95_m": 0.11
  },
  "warnings": ["B 图楼梯未复核，仅使用 z 锚点"]
}
```

指标建议（阈值待标定）：`overlap_fitness_mean < 0.05`、`floor_height_consistency < 0.1m`、`ghosting_p95 < 0.2m` 判定"可接受"。

### 4.5 N 图合并（可选，P3）

- **链式**：A+B → AB+C → …，每次沿用 4.1 流水线；要求每次锚点/重叠可用
- **全局**：把所有图的 keyframe pose 放进一个 pose graph，跨图 overlap 作为约束，GTSAM 联合优化后统一输出（工程量大，先不做）
- 无论哪种，**全局 ID 必须在合并时统一续接**（现有 `map_tool.py:1019-1026` 已做索引侧，补分配器侧）

## 5. 设计 B：跨图语义 ID 与关系表

### 5.1 全局语义 ID（拍板项）

| 方案 | 形式 | 优点 | 缺点 |
|---|---|---|---|
| A（推荐起步） | `map_id/语义id`，如 `cf09301/stair_A` | 零改动、无冲突、可读 | 字符串较长；跨图"同一楼梯"仍需关系表 |
| B | 新增 `stair_global_id`（仿 `global_keyframe_id`，用独立分配器） | 真正全局唯一，跨图直接引用 | 需要迁移/分配器/写入路径改造 |

**建议**：先 A，关系表表达"同物"；二期若多图生态成熟再升 B。

### 5.2 语义关系表（新增产物）

`<nav_root>/global_index/semantic_relations.json`（或并入各图索引，二选一，待定）：

```json
{
  "version": 1,
  "relations": [
    {
      "type": "stair_link",
      "from": {"map_id": "cf09301", "stair_id": "stair_A"},
      "to":   {"map_id": "cf09281658", "stair_id": "stair_A"},
      "relative_pose": {"x":..., "y":..., "z":..., "roll":..., "pitch":..., "yaw":...},
      "quality": {"fitness_score": 0.03, "confidence": 0.94},
      "source": "merge",            // merge | cross_map_loop | manual
      "reviewed": false,
      "created_at": "2026-10-10T16:00:00"
    }
  ]
}
```

- 与 `overlap_to` 的关系：`overlap_to` 是**帧级**证据，语义关系是**对象级**结论；生成时可引用帧级证据（global/local id + fitness）
- 生产者：离线合并（设计 A）、运行期跨图回环（可选加挂）、人工标注
- 消费者：合并工具（patch 锚点选配对）、planner（跨图/跨层路线衔接，远期）、前端（高亮同物楼梯）
- **ID 稳定性约束（v1.1 新增）**：patch/stair 引用必须绑**稳定标识**——优先 `global_keyframe_id`（永久稳定）；若必须引用 `patch_id`，需带 `pose_version`（在线草稿的 patch 编号可能在 finalize 权威重算后变化，见主题一 §4.13）
- **草稿期关系的后校验（v1.1 新增）**：在线草稿期间产生的对子/回环关系，finalize 后按权威 patch 表重新校验一遍；编号不一致的自动修正或标记待复核

### 5.3 与现有 overlap_to 的兼容

- 不改变 `overlap_to` 的写入方与 schema；仅新增 `relation_type` 取值（如 `verified_semantic_link` 预留给对象级）
- 旧图无关系表：所有消费方按"无关系"降级处理

## 6. 设计 C：在线续建（二期）

### 6.1 目标流程

```
① 加载已有图（load_map，localization）
② 定位（人工给初始位姿；主题五就绪后自动 L1/L2）
③ 进入"续建模式"（前端入口见 §6.5 的「二次建图」浮窗）：
     保留已加载关键帧/位姿图作为先验
     新关键帧按主题一的 store 追加（flushed 游标接续）
④ 边走边建（实时存储/滑窗/局部 IVox 全按主题一运行）
⑤ 保存（finalize / 另存为）：
     会话元数据（session_id）落盘
     全局 ID 续接（id_allocator 已支持）
     新旧段共同参与闭环修正
     前端统一由浮窗的「保存」或「另存为」触发
```

### 6.2 两种形态（拍板项）

| 形态 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **同一图 resume 续建**（打开工地继续施工） | 直接 resume 未定稿的 `.building`（主题一 v1.1 的 `OpenExisting` + 游标恢复）继续写；finalize 时才成为正式图 | 机制天然安全（未定稿不参与对外加载/规划）；数据只有一份 | 正式图已定稿后要续建需另开 session；仍需备份/版本管理 |
| **新图 + 父图链接**（推荐起步） | 新建 map 目录，完成后与父图离线合并（或保留链接关系） | 安全、可回退、历史可追溯 | 需要明确的父子关系字段与合并流程 |

**建议（v1.1 调整）**：主题一的 `.building` + resume 机制让"形态 A（resume 未定稿工地）"变得**可行且安全**——未定稿目录天然不对外。一期仍推"新图+父图链接"作为对外形态，形态 A 作为 resume 能力的自然延伸（主题一 P5 就绪后按需开启）；两种形态的产物续接（瓦片/粗图/语义草稿）都走同一套增量机制。

### 6.3 依赖与技术难点

| 依赖/难点 | 说明 | 已具备 |
|---|---|---|
| open/resume 存储 | 打开已有 `.building`/正式图继续写 | 主题一 v1.1 P5（`OpenExisting` + 游标恢复） |
| 产物续接 | 续建保存后由统一重烘焙流水线重算瓦片/粗图/levels（同一坐标系）；语义草稿在会话内可复用 | 主题一产物烘焙（finalize/CLI，§4.14/§4.15） |
| 自动/人工定位 | 接上旧图坐标系的前提 | 人工已有；自动=主题五 L1/L2 |
| 旧段先验接入 GTSAM | 加载图的关键帧作为先验节点，新帧作为新节点；跨会话闭环因子 | `load_map` 已重建先验因子图（`:13503-13547`）；inter-map 因子机制已有 |
| 会话边界 | `session_id`、时间戳、来源记录 | 主题一 `store_state.json` 已含 session 字段 |
| 模式切换初始化 | 从 localization 切到"续建 mapping"需重置部分状态（initializedFlag、GTSAM 增量） | 需新增，评审重点 |
| 保存语义 | 全量 vs 增量（主题一 finalize） | 主题一提供 |

### 6.4 不做什么（防过度设计）

- 不做"多机器人同时建同一张图"的并发写（文件锁/冲突合并留作远期）
- 不做在线全局优化两图的完整批量重排（先离线合并出结果，再评估）

### 6.5 前端「二次建图」浮窗（v1.3 新增，P5）

> 状态：P5 前端浮窗 + 后端续建 MVP 已编码并构建（2026-10-21）；使用 x_slam 原地切换和 `.building` 作为影子工地，尚未真机联调；完整 `.continue_sessions`/恢复机制仍按本节目标演进。
> 交互约定：二次建图的开启、保存、另存为全部在同一个浮窗内完成；原地图卡片的「保存地图」不再承担二次建图保存语义。

#### 6.5.1 入口、位置与视觉

- **入口**：设置侧边栏「可视化控制」新增「二次建图浮窗」开关（默认关，localStorage `show_continue_mapping` 持久化）；勾选后，选中/加载一张已保存地图，可视化区域显示「二次建图」卡片。该开关独立于楼层模式，和楼层卡互不依赖。
- **位置**：沿用 `FloorSwitcher` 的左上浮窗栈；楼层卡可见时放在其下方，楼层卡关闭时顶到 `top=88px`；避免遮挡地图中心、机器人和导航点。
- **视觉**：与楼层卡一致——半透明白底、8px 圆角、阴影、`z-index: 900`，宽 180~220px。
- **标题区**：标题「二次建图」，副标题显示当前地图名，状态徽标显示 `未开启 / 就绪 / 二次建图中 / 保存中 / 失败`。
- **内容区**：状态行（会话号、新增关键帧数、最后保存时间，可选）+ 三枚按钮「开启二次建图」「保存」「另存为」。
- **折叠**：卡片可折叠；折叠只隐藏内容，不停止二次建图。
- **与楼层模式的关系**：楼层卡负责“看哪层”，二次建图卡负责“是否续建、何时保存”；两者可同时显示，互不触发 `switch_map`。

#### 6.5.2 前置条件

「开启二次建图」必须同时满足：

1. 已加载一张正式地图（不能是 `buf`/未保存虚拟图），地图目录存在且可写；
2. 当前不处于建图或二次建图状态；
3. 机器人静止，当前没有正在执行的导航任务；
4. 已通过人工设位姿或自动重定位得到有效位姿，SLAM 处于可工作状态；
5. 激光、里程计、TF 正常，磁盘余量足够；
6. 当前地图没有其他写会话占用（单写者锁）。

不满足时浮窗仍可见，但「开启二次建图」置灰，并在卡片内显示具体原因，例如“请先设置位姿”“请先停止导航”“地图只读”。

#### 6.5.3 状态机与按钮

| 状态 | 开启二次建图 | 保存 | 另存为 | 界面说明 |
|---|---|---|---|---|
| 未选择地图 | 隐藏 | 隐藏 | 隐藏 | 不显示卡片 |
| 已加载、未定位 | 禁用 | 禁用 | 禁用 | 提示“请先设置位姿/定位成功” |
| 就绪 | 可用 | 禁用 | 禁用 | 显示当前地图和“可开始续建” |
| 启动中 | 禁用 | 禁用 | 禁用 | loading，禁止重复点击 |
| 二次建图中 | 禁用，文案改为“二次建图中” | 可用 | 可用 | 显示会话号、新增关键帧数、运行时长 |
| 保存中 | 禁用 | 禁用 | 禁用 | 展示阶段：flush → merge → rebake → reload |
| 保存失败 | 保持禁用 | 可重试 | 可重试 | 显示错误；原图不变，影子会话保留 |
| 保存成功 | 恢复可用 | 禁用 | 禁用 | 会话结束，卡片回到“就绪”，提示保存结果 |

补充规则：

- 「保存」和「另存为」只在“二次建图中”或“保存失败但会话保留”时可用。
- 保存成功后本次会话结束；要继续追加，需要重新点「开启二次建图」。
- 保存期间禁止关闭页面、切换地图、下发导航目标。
- 卡片右上角关闭只折叠/隐藏，不终止会话；若正在二次建图，关闭时必须二次确认“继续建图 / 放弃本次”。

#### 6.5.4 三个按钮的行为

**① 开启二次建图**

1. 校验 §6.5.2 的前置条件；
2. 在目标地图下创建**影子会话**目录 `.continue_sessions/<session_id>/`，原图在会话期间保持只读；
3. 保存会话元数据（父图、初始位姿、开始时间、操作者）；
4. 暂停导航任务，把 SLAM 从定位模式切到“续建建图模式”：旧关键帧/位姿图作为先验，新帧写入影子会话；
5. 卡片进入“二次建图中”，显示会话号和新增帧数；
6. 该过程**不调用 `switch_map`**，不重建当前显示地图，不改变地图卡片选中项。

**② 保存**

1. 要求机器人静止；若仍在移动，拒绝并提示先停止；
2. 二次确认：“将把本次续建写回当前地图，并自动备份原图”；
3. 依次执行：停止写入 → flush 关键帧 → 写 `session.json` → 合并影子会话到当前地图 → 版本号 +1 → 重烘焙产物 → 重新加载地图；
4. 写回采用“备份 + 原子替换”：先写临时目录，成功后切换；任一步失败都保持原图不变；
5. 成功后结束会话，卡片回到“就绪”，提示备份路径和新增帧数；
6. 该按钮语义是**原地保存当前地图**；不想修改原图时使用「另存为」。

**③ 另存为**

1. 弹出输入框，默认名 `<原图名>_cont_<yyyyMMdd_HHmm>`；
2. 校验地图名（非空、长度、字符集、不能已存在、不能是保留名）；v1 对已存在名称直接拒绝，不覆盖；
3. 以“原图快照 + 本次影子会话”生成新地图目录，写入 `parent_map_id`、`session_id`、`created_at`；
4. 同步 `global_index/id_allocator.json`，避免 global keyframe id 撞号；
5. 重烘焙新图产物；原图保持完全不变；
6. 成功后结束会话，提示新图名；可询问“是否切换到新图”，不自动切换。

#### 6.5.5 影子会话与落盘

推荐将“二次建图”实现为**影子会话 + 提交**，避免在线直接污染正式图：

```text
<nav_root>/<map_id>/
  .continue_sessions/
    <session_id>/
      session.json          # 会话元数据、状态、初始位姿、计数
      keyframes/            # 本次新增关键帧（按主题一 store 格式）
      traj/                 # 本次轨迹/位姿增量（按需）
      products/             # 本次会话临时产物（按需）
```

- 会话期间原图的 `global_map.pcd`、`keyframe_index.json`、`nav_light/`、`levels/` **只读**；
- `保存` 时把影子会话合并进当前图，并在 `<nav_root>/backups/<map_id>_<timestamp>/` 留完整快照；
- `另存为` 时复制原图 + 影子会话生成新图，不改原图；
- 影子会话只允许一个活动写者，通过 `.continue_sessions/active.lock` 或后端内存锁防止多浏览器并发；
- 浏览器刷新、网络断开、后端重启后，卡片应能通过 `session.json` 恢复“检测到未完成会话”，由用户选择继续或放弃；**不自动合并**；
- 放弃只删除影子会话，不动原图。

#### 6.5.6 与导航、切图、异常的关系

- **导航**：二次建图期间暂停导航；禁止新导航目标；如果检测到导航任务，先拒绝开启并提示停止。
- **切图**：二次建图期间禁止 `switch_map` 和加载其他地图；用户点其他地图卡片时提示“请先保存或放弃本次二次建图”。
- **楼层浏览**：仍然允许切浏览层，纯显示行为，不影响二次建图。
- **保存失败**：原图不变，影子会话保留，卡片显示失败阶段和原因，可重试保存/另存为。
- **服务重启**：从 `session.json` 恢复状态；无法恢复时标记 orphan，只允许放弃或导出，不自动写原图。
- **权限/磁盘不足**：开始前预检；保存前再次检查；失败不产生半成品正式图。

#### 6.5.7 接口与前端组件（建议）

| 类型 | 名称 | 说明 |
|---|---|---|
| HTTP | `POST /api/extra/continue_mapping/start` | 入参 `{map_name}`；创建影子会话，返回 `session_id/parent_map_id/state` |
| HTTP | `GET /api/extra/continue_mapping/status?map_name=...` | 返回状态、会话号、新增帧数、最后错误；卡片轮询/恢复用 |
| HTTP | `POST /api/extra/continue_mapping/save` | 入参 `{session_id}`；原地保存当前地图，返回备份路径、版本、报告 |
| HTTP | `POST /api/extra/continue_mapping/save_as` | 入参 `{session_id,new_map_name}`；生成新图，返回新图名和父图关系 |
| HTTP | `POST /api/extra/continue_mapping/abort` | 入参 `{session_id}`；放弃影子会话；不修改原图 |
| 前端 | `ContinueMappingCard` | 与 `FloorSwitcher` 同区域堆叠；按钮/状态机见 §6.5.3 |
| 前端 | `continueMapping` service | 封装上述 HTTP；禁止前端直接拼路径 |

接口约束：

- `map_name/new_map_name` 必须走地图白名单和字符集校验，禁止路径穿越；
- `save/save_as/abort` 必须携带当前 `session_id`，重复请求要幂等；
- 会话不存在返回 404，会话冲突/已有写者返回 409，地图只读返回 423；
- 前端所有按钮请求期间置灰，防止连点造成双写。

#### 6.5.8 验收要点

1. 未定位时「开启」禁用；定位成功后启用；
2. 开启后不触发 `switch_map`，原地图仍可正常显示，卡片显示“二次建图中”；
3. 保存成功后当前地图包含新区域，原图有备份，版本号增加；
4. 「另存为」生成新图，`parent_map_id/session_id` 正确，原图字节级不变；
5. 保存/另存为失败时原图不变，影子会话可重试/放弃；
6. 二次建图期间切图、导航、重复保存均被阻止；
7. 浏览器刷新/服务重启后能识别未完成会话，不自动写原图；
8. 新增关键帧的 global id 不冲突，重烘焙后地图可加载、可导航。

### 7.2 渲染设计（web_app，Three.js）

- **箭头/圆锥**表示每帧位姿（yaw 朝向；roll/pitch 可忽略或微调颜色）
- **着色**：按 `map_id` 区分（多图叠加时）；或按时间渐变（看轨迹顺序）
- **重叠连线**：`overlap_to` 的关系对子画连线（跨图回环成功与否一目了然）
- **点选**：显示 `global_keyframe_id`/位姿/时间；多图时显示来源 map
- **anchor 选择工作流**：点击两图中"应为同一处"的帧 → 生成 `--a-anchor i --b-anchor j` 命令（复制到剪贴板或一键调后端工具）
- 性能：单图几百帧无压力；万帧按视口/楼层过滤

### 7.3 与主题二/四的复用

- 图层开关并入主题四的图层管理（关键帧/patch/楼层/瓦片）
- 分块加载后，位姿图层仍走 HTTP（不依赖点云是否已加载），保证"先看骨架再看肉"

## 附录 A：专业名词详解

> 按"是什么 → 为什么 → 在本方案中的角色"三段式。

### A1. map_id
- **是什么**：地图目录的名字（如 `cf09301`），是"一张图"的身份标识；写在 `keyframe_index.json` 顶层和每个关键帧条目里。
- **为什么**：一个根目录下可以有很多图；跨图逻辑必须先分清"哪些帧属于哪张图"。
- **本方案角色**：判断"同图/跨图"的唯一依据；合并、关系表、前端多图着色都以它分组。

### A2. local / global keyframe id
- **local_keyframe_id**：图内帧号，从 0 开始（`surf/<i>.pcd` 的 i 就是它）。
- **global_keyframe_id**：跨所有图唯一的帧号，由分配器统一发号。
- **为什么**：两张图都有"第 5 帧"，合并后必须能唯一引用；全局帧号让"哪张图的哪一帧"永远不歧义。
- **本方案角色**：`overlap_to`、关系表、GTSAM 跨图因子都用全局帧号引用目标。

### A3. id_allocator.json
- **是什么**：`<nav_root>/global_index/id_allocator.json`，只记一件事：下一个可用的全局帧号（如 `next_global_keyframe_id: 3956`）。
- **为什么**：多个图共享一个发号器，才能保证不撞号；比每次扫描所有图的最大号更省。
- **本方案角色**：合并/续建后必须同步推进；否则下一次建图会发出已被占用的号。

### A4. overlap_to
- **是什么**：关键帧条目里的一个数组，记录"本帧与别的图某帧重叠"的证据：目标帧的 global id、map_id、相对位姿、fitness、confidence。
- **为什么**：让跨图关系持久化，供运行时建因子、离线审计。
- **本方案角色**：帧级证据；语义关系（对象级）从它提炼，合并流程可引用。

### A5. 跨图回环（inter-map loop）
- **是什么**：机器人建图时发现"现在看到的地方，在另一张已保存的地图里也有"→ 用 ICP 求出两图相对位姿 → 写 `overlap_to` 并给 GTSAM 加约束。
- **为什么**：让两张图在算法层面"接上"，纠正跨图漂移。
- **本方案角色**：运行期已有的能力；离线合并复用同一套验证思路（ICP + fitness）。

### A6. ICP / GICP / fitness score
- **ICP**：经典点云配准算法——反复配对最近点、求最小变换、迭代，直到收敛。**GICP** 是它的推广（考虑局部几何分布）。
- **fitness score**：配准质量分数（点到最近点的平均残差类指标），越小说明对得越齐。
- **为什么**：ICP 是"局部优化"，初值差会配错——所以需要粗对齐（seed/anchor/patch 锚点）。
- **本方案角色**：精配准器 + 质量评估依据。

### A7. seed 与 anchor（合并粗对齐）
- **seed**：直接给一个相对位姿（`x y z yaw`）作为初值。
- **anchor**：指定"图 A 的第 i 帧和图 B 的第 j 帧是同一处"，用两帧位姿反推相对变换。
- **为什么**：ICP 需要一个不太离谱的起点。
- **本方案角色**：现有两种粗对齐方式；本设计新增第三种：**patch 锚点**（更自动化）。

### A8. patch（面片）
- **是什么**：楼梯语义的最小面片单元，带编号与几何范围。类型有 `floor`（楼板）、`stair_entry`/`stair_exit`（楼梯出入口）、`tread`（踏面）；字段含 `patch_id/stair_id/flight_id/step_index/mean_z/bbox/reviewed`。
- **为什么**：跨层导航要按级踏面规划与校验；也让地图有了"语义对象"。
- **本方案角色**：合并的语义锚点来源（floor mean_z 提供 z、楼梯轴向提供 yaw）。

### A9. floor mean_z（楼层平面高度）
- **是什么**：某个楼层面片内点的平均高度。
- **为什么**：比单个点稳；楼层平面是地图里最可靠的水平基准。
- **本方案角色**：z 锚点——两张图的同名楼层高度差，就是垂直对齐量。

### A10. stair 轴向 / yaw
- **是什么**：楼梯从入口到出口的方向（水平面内）。yaw 是绕垂直轴的旋转角。
- **为什么**：走廊/货架区方向特征弱时，ICP 可能转错 180°；楼梯轴向是强方向特征。
- **本方案角色**：yaw 锚点——两图楼梯轴向夹角即初始旋转修正。

### A11. pose graph / GTSAM
- **是什么**：把每帧位姿当"节点"，把相对测量（里程、回环、跨图重叠）当"边"，做全局最小二乘优化。GTSAM 是常用库（本系统 ISAM2 增量求解）。
- **为什么**：建图误差会累积；闭环/跨图约束能把它"拉回"。
- **本方案角色**：跨图回环因子已接入；续建时新旧段共同参与优化。

### A12. reviewed（复核标志）
- **是什么**：patch/楼梯语义里的布尔字段，表示"该语义已被放行采用"；由**自动几何门（`validate_and_gate`：级数/宽度/级高/覆盖率等十几项检查）+ 放行策略**产生。
- **为什么**：自动几何门只能证明"几何自洽"，不能证明"语义正确"（这真是楼梯吗、对应哪部、回退生成是否可信）——所以线上保存路径稳妥地强制 `reviewed=false`（CLI 默认"自动门过即 `true`"），最终由人工/抽查放行。
- **本方案角色**：合并锚点只信 `reviewed=true` 的 patch；否则降级（cf09301 就是这种状态）。

### A13. session / 续建
- **session**：一次建图过程（从开始到保存）的标识。
- **续建**：在已有地图坐标系上继续建图，新帧追加到同一数据体系。
- **为什么**：大场景一次建不完；多会话天然存在（分楼层、分批）。
- **本方案角色**：主题一本 `session_id` 字段；在线续建是终极形态，离线合并是当前形态。

### A14. 父图链接（parent_map_id）
- **是什么**：新图记录"我是在哪张图的基础上续建的"。
- **为什么**：追溯来源、批量合并、避免误当独立图处理。
- **本方案角色**：推荐续建形态（新图+父图）的追溯字段。

### A15. keyframe_index.json
- **是什么**：地图的"户口本"：每帧的全局/局部编号、位姿、文件路径、重叠关系、版本号。
- **为什么**：加载、合并、显示都可以只读它（KB 级）而不碰点云。
- **本方案角色**：合并输入/输出、前端位姿图层的数据源。

### A16. merge_report（质量报告）
- **是什么**：合并后生成的 JSON 报告：用了什么对齐、评分如何、有哪些警告。
- **为什么**：合并是否可信，必须可量化、可复核，而不是"看起来还行"。
- **本方案角色**：验收凭据 + CI 检查项。
