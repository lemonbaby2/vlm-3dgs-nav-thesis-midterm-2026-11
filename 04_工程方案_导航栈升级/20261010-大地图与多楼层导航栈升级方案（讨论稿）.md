## 0. 摘要（TL;DR）

六个主题，一条主线：**索引常驻、数据按需、建图随写、按层呈现、自动重定位**。

| 主题 | 一句话 | 优先级 |
|---|---|---|
| 一、建图过程实时存储 | 关键帧随产随写，内存只留滑窗，派生图后台烘焙 | P0 |
| 二、地图加载按需化 | 落地 260827 Spec + 关键帧按需 + 分块 LOD + 前端瓦片 | P0 |
| 三、保存后二次建图 | 关键帧匹配 + patch 语义锚点，先离线合并、再在线续建 | P1 |

核心原则：**一套索引底座（chunk/level/关键帧）服务所有主题；所有 schema 变更集中管理（见第 9 章）；每一步可开关、可回退、零回归。**

## 1. 背景与问题清单

### 1.1 已有现状（详见背景篇）

1. `load_map` 全量加载，存在 4 次整图级扫描（读全部关键帧 PCD → 全局 IVox → 拼 `localization_loaded_map_` → 显示拼接降采样），见 `x_slam_大地图加载耗时分析.md:52-61`
2. 同一时间内存端着多份整图副本（关键帧容器、全局 IVox、loaded_map、显示拼接临时云）
3. `/x_nav/global_map` 固定以最后关键帧为中心、600m 半径发布，不随机器人滚动
4. 前端整图收 Foxglove WS + 累加 100 帧，无分块/无 LOD
5. planner 侧再全量读一遍 `global_map.pcd` 建 KD-Tree/体素图/SDF/拓扑（`x_planner.cpp:5712/5728`）

### 1.2 本次新增问题（2026-10-09/10 讨论）

| # | 问题 | 证据/说明 |
|---|---|---|
| 1 | 建图全程只进内存，结束时才 `save_map` 一把写 | `save_map` 是唯一落盘入口（`laser_mapping.cc:6889-6891`），无周期写盘；关键帧容器随里程线性增长 |
| 2 | 无多会话续建通道 | `load_map` 后进入定位模式；localization/mapping 是两种启动模式，无"定位后续建"路径 |
| 3 | 多层预览无法按层过滤 | patch 是平面；`ground_levels` 只有 z 聚类；前端无按层加载能力 |
| 4 | 关键帧位姿无前端展示 | 后端已有 `/x_nav/keyframe_graph` 话题和 `keyframe_index.json`，前端未消费 |
| 5 | 无自动重定位 | 现有能力需要人工/外部给大致位置（initialpose/GPS）；代码无全局描述子检索（仅多候选 GICP） |
| 6 | 换图/换层与导航耦合 | `switch_map` 会重启 slam/planner，前端切楼层若无约束会中断导航 |
| 7 | 回环检测在大图上失效 | 候选搜索依赖位姿 3m 半径（`historyKeyframeSearchRadius: 3`），漂移超过半径后永远检测不到；无长程描述子检索 |
| 8 | 全局导航与全精度点云强绑定 | planner 启动全量加载派生全部结构，缺少"全局轻量层 + 区域按需"的分层 |

### 1.3 一句话目标

**索引常驻、点云按需、建图随写、按层呈现、自动定位。**

## 2. 目标与原则

### 2.1 目标

1. 内存有硬上限：建图内存不随里程线性增长；加载内存不随地图规模线性增长
2. 启动与地图规模解耦：启动只读 K 级索引，秒级到可定位
3. 保存崩溃安全：任意时刻断电，最多丢尾部少数帧，地图可恢复
4. 多会话地图可维护：离线可合并、可验证对齐；在线可续建（二期）
5. 多层楼体验：预览/加载按层；全局小地图导览式切换
6. 自动重定位：无初始提示下自动消歧（L1+L2），人工提示降为兜底

### 2.2 原则

- **零回归**：所有新行为带开关，默认关闭时与现状行为一致；参考 P0/P1 跨楼层升级的"默认全关"先例
- **复用优先**：旧分块协议（chunk_mapping/end_chunk/save_chunk、`chunks/index.txt`）、`keyframe_index.json`、`global_index`、楼梯语义、多候选 GICP 全部复用
- **数据格式向后兼容**：新增字段只做扩展，旧地图可读；旧地图可离线补齐新产物（levels/描述子/分块）
- **改动分层**：算法侧（x_slam/planner）、协议侧（索引/接口）、前端侧（web_app）分批落地，互不阻塞
- **点云只写一次**：点云文件局部坐标系直存（surf=imu 系、ground/obs=base 系），闭环只改位姿——所有存储方案建立在这条之上

## 3. 主题一：建图过程实时存储（内存有界）

> 已细化：见同目录《20261010-主题一-建图过程实时存储（详细设计）.md》。

### 3.1 现状与风险 【已确认】

- 建图全程只进内存：`surf_CloudKeyFrames_imu`、`ground_CloudKeyFrames_lidar_`、`noground_CloudKeyFrames_lidar_` + 位姿容器 + GTSAM 图
- 有界项：IVox（40000 体素 LRU + 50 点/体素，`x_nav.yaml:131-133`）、MapIncremental（TTL）
- 无界项：**关键帧点云容器**（主风险）、GTSAM 因子图（K 级，较小）
- 保存行为：快照只拷贝 shared_ptr 向量（`laser_mapping.cc:10926-10948`），不复制点云；但会新建 `global_map.pcd`/`global_ground_map.pcd`/downsize（额外一份瞬态副本）——**爆内存主要发生在建图过程，不是保存瞬间**
- 量级参考（cf09301 实测）：单帧 surf 141KB / obs 48KB / ground 6.5KB ≈ 200KB 磁盘，内存更重；1000 帧 ≈ 数百 MB

### 3.2 方案 【方案】

```
新关键帧定稿
  → ① 入内存（现有逻辑不变）
  → ② 投递异步写任务：surf/ground/obs/<i>.pcd（tmp + rename，批量 fsync）
  → ③ 位姿追加 poses_*.txt；每 N 帧刷新 keyframe_index.json / map_block_meta.json
  → ④ 已落盘且超出滑窗的原始点云释放（滑窗：最近 M 帧或 R 米，建议 M=100~200 / R=30m，待定）
  → 位姿索引常驻（K 级）；局部匹配需要的旧帧按需读盘 + LRU 预取
收尾 save_map：
  → 只刷尾部帧 + 重写位姿（带 pose_version）+ 后台烘焙 global_map/ground/downsize
```

要点：

1. **异步写线程**：绝不在雷达回调线程写盘；写队列限速；单文件 tmp+rename；**禁止逐帧 fsync**，按批触发
2. **内存滑窗**：被释放的只是"已落盘的原始点云"，位姿 KD-Tree、GTSAM、索引全部保留；局部匹配需要远端帧时走按需读取
3. **派生图延迟烘焙**：`global_map.pcd` / `global_ground_map.pcd` / downsize 收尾或后台增量重烘焙；`map_block_meta.json` 预留的 `pose_dirty` / `derived_map_dirty` 字段正式接线
4. **闭环修正**：优化只改位姿 → 位姿文件版本化（`pose_version`），最终保存重写位姿 + 重建索引；**点云文件永不重写**
5. **崩溃恢复**：维护"已落盘帧游标"（参考预留字段 `flushed_pose_version`）；断电后 load 时校验并截断半帧；沿用 `.saving/.backup` 事务语义
6. **旧协议复用**：`chunk_mapping` / `end_chunk` / `save_chunk` 与前端 `SlamChunkStatusData` 字段（`web_app/src/types/api.ts:93-110`）就是这套东西的前身，建议直接复活

### 3.3 验收

- 长时间建图内存曲线平稳（有上限，不随里程增长）
- 写盘对 SLAM 帧处理耗时影响可忽略（指标待定：如 P99 增量 < 5ms）
- 断电恢复测试：kill -9 后重启，地图可加载且不出现半帧损坏

### 3.4 风险与回退

| 风险 | 缓解 |
|---|---|
| 写盘抖动影响实时性 | 独立线程 + 队列 + 限速 + 批量 fsync；指标监控 |
| 存储磨损/容量 | 容量水位监控；已归档块滚动清理（配合分块） |
| 滑窗释放影响远端匹配 | 预取 + LRU；先小步放开（先用滑窗只释放最老帧） |
| 回退 | 开关一关恢复"全程内存 + 收尾一把写" |

### 4.2 关键帧按需读取 【方案】

- 启动只读：`poses_*.txt` + `keyframe_index.json` + chunk 索引 → 建位姿 KD-Tree（K 级，秒级）
- 首次定位/跟踪：按位姿 KD-Tree + chunk 索引**只读附近关键帧 PCD** → 局部子图 → 局部 IVox
- 运行期：LRU 缓存（按内存预算，建议 1~2GB，待定）+ 运动方向预取
- 显示不再依赖内存关键帧容器：全图用 downsize/LOD 产物

### 4.3 分块与 LOD 产物 【方案】

- 物理存储不变（`surf/ground/obs/<i>.pcd` 原子性/回滚成熟），**chunk 是索引 + 显示产物**
- 协议复用旧设计（`release_notes/2605/260520/commu.md:165-177`；前端字段 `web_app/src/types/api.ts:24-47`）：
  - 2D 网格 `floor(x/chunk_size), floor(y/chunk_size)`；chunk_size 起步 20~50m（待定）；`buffer_width` 5~10m（查询光晕，不重复存点）
  - 按**关键帧位姿**入格（不拆帧）；多楼层网格只在 x/y 分块，元数据带 z_range/level
  - chunk 产物：关键帧 id 列表、bbox、L1 降采样（0.2~0.3m）、`version`（闭环/合并后 +1，前端缓存失效）
  - `chunks/index.txt`（或 json）与前端 `MapChunkData` 对齐
- 后端接口：`get_map_chunks`（前端已声明未实现，`web_app/src/constants/api.ts:40`）+ 瓦片静态文件服务（`?level=&x=&y=&v=`）
- 生成方式：**finalize 烘焙（C++）+ 旧图 CLI `semantic_tool tile` 补算**；合并后统一重烘焙（不做在线切割）

### 4.4 前端数据通道重构 【方案】

- **静态地图走 HTTP**：全局/分层/分块预览为带版本号的静态文件，可缓存、断线可恢复
- **实时数据留 Foxglove WS**：`current_pointcloud`、障碍、导航点等
- 删除"整图订阅 + 累加 100 帧"（`web_app/src/pages/index/index.tsx:171-172`）
- TileManager：视口 + 距离选 LOD；AbortController 取消移出视野请求；Worker 解析；内存预算 + LRU；渐进式（低清占位 → 高清替换）

### 4.5 验收

- 大图启动到可定位时间显著下降（与地图规模解耦，目标秒级，基线待实测）
- 加载期内存不随地图规模线性增长
- 前端首屏只拉当前视口瓦片；浏览器内存/帧率稳定

## 5. 主题三：保存后二次建图（多会话拼接）

> 已细化：见同目录《20261010-主题三-保存后二次建图（详细设计）.md》。

### 5.1 现有能力与缺口 【已确认】

- 已有：`map_id`（=目录名）、`global_keyframe_id`（`id_allocator.json` 全局分配，`laser_mapping.cc:1323-1346`）、跨图回环检测（`FindInterMapLoopCandidate:1056-1114`）、overlap 落盘（`MakeOverlapTargetJson:755-813`）、跨图 GTSAM 因子（`:1223-1234`）、离线合并 `map_tool.py merge`（anchor/seed + 可选 ICP）
- 缺口：
  1. 在线续建无通道（`load_map` 后只有定位模式）
  2. 合并缺语义锚点（纯 ICP 在平坦区域 z 不可观）
  3. 跨图语义 ID 不统一（`stair_A` 每图各自命名）
  4. patch 可能缺失/被拒（cf09301 现状：`stairs.rejected-anchor-20261009`，quality `trajectory_fallback`）

### 5.2 离线合并增强 【方案】

- **关键帧匹配为主**（现有 ICP/overlap），**patch 为语义锚点**：
  - z 对齐：floor patch `mean_z` 之差（cf09301 floor_0=2.85 / floor_1=5.59）
  - yaw 初值：stair `entry→exit` 方向
  - 楼层对应：`from_floor_id`/`to_floor_id` + stair_graph
- `map_tool.py merge` 增加 `--patch-anchor`（有 patch 用，无则退化现有流程）
- 测试样例：cf09301 + cf09281658（计划中的合并预演，`20261009 总结文档` 第 6 节）

### 5.3 跨图语义 ID 与关系表 【方案】

- 全局语义 ID 规则：`map_id/stair_id` 或新增 `stair_global_id`（拍板：**【待定】**）
- 关系落盘：A 图 `stair_A` ↔ B 图对应楼梯的对应关系（仿 `overlap_to` 结构：双方 map_id + id + 相对位姿 + fitness/confidence）
- 复用 `overlap_to` 已有写入机制，扩展 relation_type（如 `verified_semantic_link`）

### 5.4 在线续建模式（二期）【方案】

```
load_map（加载已有图，定位模式）
  → 重定位成功
  → 切换到"续建模式"：保留已加载关键帧/位姿图作为先验
  → 新关键帧追加（global id 续接，id_allocator 已支持）
  → save_map 全量写出（或增量，依赖主题一）
```

- 依赖：主题一的实时存储基础 + 模式切换的状态初始化
- 风险：旧图先验与新会话漂移的衔接（闭环修正要覆盖新旧两段）

### 5.5 关键帧位姿前端图层 【方案】

- 数据源：`/x_nav/keyframe_graph`（实时；latched MarkerArray：黄点节点 + 蓝/粉边，`laser_mapping.cc:2503/2711-2806`，load 后也有快照 `:13566`）+ `keyframe_index.json`（离线/多图，含 6DoF + `overlap_to`）
- 新增 HTTP：`get_keyframe_poses?map=...`（含 id/map_id/位姿/时间/is_overlap/overlap_to）
- 渲染：每帧箭头（yaw 朝向）、按 map_id 着色、按时间渐变、点击显示 id/位姿、overlap 连线
- 用途：选 merge anchor、验证新旧轨迹对齐、检查跨图回环配对

### 5.6 验收

- cf09301+cf09281658 合并：对齐误差（重叠区重影/ICP fitness）、层高一致、导航点变换正确
- 关键帧图层：170+150 帧流畅渲染，anchor 选择可用

## 6. 主题四：多层楼与前端地图体验

> 已细化：见同目录《20261010-主题四-多层楼与前端地图体验（详细设计）.md》。

### 6.1 levels 产物烘焙 【方案】

**原理：patch 是 2.5D 平面片，楼层切分 = 高度层 + 平面范围 + 高度窗口三者的组合**：

```
本层点云 = ground_levels 的 z（楼层高度）
         ∩ floor patch bbox/多边形（平面范围）
         ∩ 高度窗口 [floor_z - 0.3m, floor_z + 2.5~3m]（墙/家具保留，天花板/上层排除）
楼梯点 → 归相邻两层（或单独 transition 层）
```

- 新增产物（保存/离线时生成）：
  ```
  levels/index.json          level_id / mean_z / z_range / floor polygon / 相邻楼梯(stair_id)
  levels/<id>/preview_downsize.pcd   每层低清预览
  levels/stairs_<stair_id>.pcd       楼梯过渡层（归相邻两层显示）
  ```
- 生成工具：**finalize 烘焙 + 旧图 CLI `semantic_tool levels` 补算**（楼层带草稿在线，仅作可用性输入）
- 无 patch 退化：只用 `ground_levels` + 2D 高度图找脚下楼层
- 更精细方案（可选/后续）：预计算每点楼层标签（最近地面层/洪水填充）

### 6.2 预览按层加载与切换 【方案】

- 普通预览模式只加载当前层文件；上下楼梯时依据 `stair_graph`（`from_floor_id`/`to_floor_id`/edges）切相邻层
- **切楼层 = 纯前端换文件，绝不触发 `switch_map`**（现状 switch_map 会重启 slam/planner）
- 机器人实际导航所在楼层由 SLAM/planner 决定（`ground_levels` 匹配），与前端浏览楼层解耦

### 6.3 全局压缩小地图（商场导览图）【方案】

- 素材：`global_map_downsize.pcd`（cf09301 仅 205KB）+ 每层 downsize（几十 KB）
- 前端（web_app 已 Three.js）：
  - 角落第二视口（独立 canvas 或 renderer viewport/scissor）
  - 正交俯视（导览图风格）或透视；主相机 yaw 同步；机器人位置用 odom 画箭头
  - 切层交互：层号列表点击 / Raycaster 拾取楼层组；点击定位 → 主视口聚焦或下发导航目标
  - 数据走 HTTP，不占 Foxglove WS
- 与楼梯导航联动：点击楼梯高亮 `stair_A` 并提示换层（数据来自 stair_graph）

### 6.4 图层管理 【方案】

- 图层开关：关键帧位姿层 / patch 层 / 楼层层 / 导航点层 / 实时障碍层
- 点选交互：关键帧（id/位姿/时间）、patch（stair_id/step_index）、重叠关系连线

### 6.5 验收

- 前端帧率/内存稳定（万级点数 + 多层切换）
- 切层耗时（目标 < 1s，待定）、切换过程导航不中断

## 7. 主题五：自动重定位（L1 + L2 + L3）

> 已细化：见同目录《20261010-主题五-自动重定位（详细设计）.md》。阶段性说明：自动重定位排期靠后（主题六优先），当前先以人工/GPS 种子为准。

### 7.1 现状与能力边界 【已确认】

- 现有：人工/外部给初始位姿（initialpose/GPS）+ 多候选分阶段 GICP（`relocalization_random_mode_`、`ProcessLocalizationInitialization`）；代码中**无**全局描述子检索
- 边界：单帧 + 无先验 + 局部配准 → 相似走廊/对称结构/多层相似布局产生多解（感知歧义）；完全对称且零线索是理论不可解上限

### 7.2 L1 全局描述子检索 【方案】

- finalize 时对每个关键帧预计算全局描述子（C++；候选技术：Scan Context / LiDAR-Iris / M2DP，轻量无需训练；**【待定】**选型）
- 存储：`keyframe_index.json` 扩展字段或独立 `descriptors.bin`（格式待定）
- 运行时：检索 top-k（3~8）→ 复用现有子图 GICP 验证打分 → 楼层用 `ground_levels` 过滤
- 产出：自动给出"大致位置"，人工提示降为兜底

### 7.3 L2 多假设序列消歧 【方案】

- 数据流：

```
L1 top-k → 初始化假设集（幽灵位姿 + 权重，跨帧存活）
循环（2~5Hz 限流）：
  假设预测 → 子图 GICP 打分 → 权重更新/淘汰
  → 发布状态（假设列表 + 权重 + 建议动作）
收敛：top1 权重领先（如 >80%）且连续 N 帧一致 → handoff 正常跟踪
```

- 关键机制：
  1. **假设跨帧存活**（消歧的本质），不是每帧重检索
  2. 多帧一致性判据（防单帧误杀/误判）
  3. 运动策略：**优先原地旋转**（四足最安全）→ 短距离直行/小 S 形；消歧期限速、禁导航任务、全功率避障
  4. 主动重定位：自动选择"最有区分度"的小动作（方案：旋转角优化；**【待定】**）
- 状态机：`未定位 → 检索中 → 消歧中 → 定位成功 → 跟踪中`（+ 丢失重捕）
- 接口：
  - 话题 `/x_nav/relocalization/state`（状态 + 假设位姿 + 权重 + 建议动作）
  - 命令（`/node_cmd` 或 web API）：`relocalize_start/rotate/advance/confirm/reject/set_initial_pose`

### 7.4 L3 外部线索兜底 【方案】

- 楼层约束（ground_levels）、App 选楼层/点大致区域（人工版）、UWB/WiFi/二维码/GPS（户外）

### 7.5 前端引导设计 【方案】

| 区块 | 内容 |
|---|---|
| 状态区 | 大字状态（消歧中/成功/丢失）、置信度条、top1-top2 分差（犹豫度）、未定位时导航按钮置灰 |
| 假设可视化 | 半透明幽灵机器人（透明度=权重）、最优高亮、候选编号与权重标注；收敛过程可见 |
| 动作引导 | `原地旋转一圈（推荐）`/`向前 2 米`/`暂停`按钮 + 进度（旋转角度/收敛帧数）；建议动作来自 state 话题 |
| 自动/手动 | 默认自动执行旋转/短移动，操作者可随时接管 |
| 人工兜底 | 小地图点楼层+区域给初始位姿（回 L0）；"定位不对"一键重定位 |
| 安全防呆 | 限速状态、障碍提示；30s 不收敛自动停 + 提示人工 |

### 7.6 验收

- 首次重定位成功率、top-k 命中率、收敛时间/行走距离、**误定位率（尤其串层率）**、消歧期 CPU
- 离线 bag + 实机（cf09301 多层场景）

## 8. 主题六：大地图全局导航（分层加载 + 回环）

> 已细化：见同目录《20261010-主题六-大地图全局导航（详细设计）.md》（导航概念详解、改造清单 A1~A11、参数与验收都在其中）。自动重定位（主题五）排期靠后，本节不含。

### 8.1 核心结论 【方案】

- 全局规划的最小依赖 = **全楼粗略能走图 + 楼梯连接 + 目标坐标**（几百 KB~几 MB），不需要全精度点云
- 现状 planner 全量读 `global_map.pcd` 并派生 kdtree/Vox_map/SDF/拓扑（`x_planner.cpp:1194-1201/5897`），成本与地图规模绑定

### 8.2 分层架构 【方案】

| 层 | 内容 | 驻留方式 |
|---|---|---|
| 全局轻量层（新增 `nav_light`） | 每层粗栅格（0.5m，保守生成）+ 拓扑 + 楼梯语义 + ground_levels + 导航点 | 常驻（MB 级） |
| 区域细图层 | 复用主题二 chunk/LOD 瓦片；区域 Vox/SDF | 按需（LRU + 预取） |
| 局部执行 | 现有 ego 窗口/避障/动态障碍 | 逻辑不变，仅换数据来源 |

流程：目标映射（层+粗格）→ 粗图 A*（跨层经 semantic patch sequence）→ 走廊路径 → 区域细图加载与走廊修正 → 现有局部执行。

### 8.3 导航数据关系（楼梯 / 普通地面 / patch）【已确认】

- 点云层：楼梯踏面与普通地面同为 "ground" 点，**无编号、无连接**
- 几何连接：`ground_graph`（半径 1m 连边 + **z 突变 0.35m 否决**）→ 台阶逐级连通、楼层自动断开
- 语义连接：`stair_patches` + `stair_graph`（patch 节点 + 显式边 `delta_z_m/gap/confidence`）
- 楼层层：`ground_levels`（z 聚类 + `stair_like`）用于楼层过滤
- 点云与 patch 的关联是**空间匹配**（bbox + mean_z 查询），没有点级链接

### 8.4 大地图回环检测（地图一致性）【方案】

- 现状：建图 1Hz，位姿 **3m 半径**找历史候选 + ICP（`fitness<0.3`）→ GTSAM 修正（`detectLoopClosureDistance:12089`）
- 问题：3m 半径依赖位姿，**漂移 >3m 后永远检测不到**；相似环境/多层相似存在误检
- 增强（两层回环）：短程保留现有；**长程用描述子检索**（复用主题五产物，不受漂移距离限制）+ ICP 验证
- 防误检：多帧一致性（连续 3~5 帧）+ 描述子/fitness 双门槛 + 楼层约束（跨层必须经 stairs）
- 成本控制：ISAM2 增量 + 回环冷却；闭环后局部 IVox 按 Spec 重建（唯一硬例外），`nav_light`/`chunks`/派生图标 dirty **后台重烘焙**
- patch 与回环的关系（骨架不变、语义增强：楼层护栏 / 楼梯步级校验 / 跨会话锚点）见主题六文档 §7.5

### 8.5 必要改造清单（摘要，详见主题六文档第 8 章）

| 阶段 | 改造项 |
|---|---|
| P0 | A1 `nav_light` 烘焙 → A2 planner 只读轻量层 → A3 粗图全局规划（含跨层拼接） |
| P1 | A4 区域细图加载器 → A5 区域 Vox/SDF → A6 目标/最后一段 → A7 版本一致性 |
| P2 | A8 `ground_graph` 升格常驻 → A9 长程回环 → A10 闭环后轻量层重建联动 → A11 监控 |

### 8.6 验收

- planner 启动时间/内存与地图规模解耦；全局路径与现状回归对照正确（含跨层、不穿墙）
- 漂移 >3m 的长程回环可检出且误检受控；闭环后轻量层自动更新
