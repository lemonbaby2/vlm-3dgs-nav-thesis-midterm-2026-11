## 1. 一句话结论

主题二的核心目标——**把"启动/切图成本"和"内存占用"从"地图规模"解耦**——已实现：定位加载由"全量载入"改为**按需流式读取**，启动耗时稳定在 ~0.1s、近场数据冷读 ~24ms/热读 0ms，且与地图大小无关；保存、烘焙、前端底图三条链路均有对应产物与回退开关。

## 3. 真机验证数据汇总（cf0930 / cf09281658 / cf09301）

**加载与取件（cf0930，定位模式）**

| 指标 | 数值 |
|---|---|
| 加载耗时（旧全量 → P3 v1 → P3b） | 0.150s → 0.171s → **0.104s** |
| 重定位窗口（冷启动，48 帧 + 13 帧预取共 61 帧读盘） | `io_max=0.9ms` / **`io_total=23.6ms`** |
| 重定位窗口（缓存命中） | **0.0ms** |
| 窗口常驻 | `resident=48 failed=0 window=48` |
| 预览点云 | `global_map=23274 pts` / `global_ground=2105 pts` |

**保存（定位模式，cf0930）**：surf/ground/obs = **131/131/131（33MB）** 成功。

**P4-3 校验**：正常图 PASS；两条拒绝原文——
- `coverage check: surf frames (130) < keyframe_index count (131); refusing to finalize`
- `coverage check: chunks/index.json source_pose_version (99) != keyframe_index.pose_version (1); refusing to finalize`

**P4-1 实测（L0 体积 vs 流式成本）**

| 叶大小 | chunks 体积（cf0930） | 备注 |
|---|---|---|
| 0.3（现网 lod1，默认） | **496 KB** | 现场默认 |
| 0.2 | 876 KB | |
| 0.1（≈ lod0/L0） | **2080 KB** | **约 4.2× lod1**，随规模/层数放大，每次重烘焙重算 |

**P4-1 结论**：保持流式（不落 L0）。流式成本极低且与规模无关（窗口半径有界，冷读 ~24ms/热读 0ms），L0 仅省这 ~20ms 却带来 4× 磁盘与额外维护。复核触发条件：出现 `io_max` 持续 >300ms（慢盘/网络存储）或超大图窗口读盘成为瓶颈时再评估（CLI 已支持 `--lod1-leaf` 手工验证）。

## 4. 开关与回退一览

**x_slam 参数（现场 `nav_map/x_nav.yaml`，默认关闭）**
- `on_demand_load_enable`：按需读取总开关（surf/ground/obs 不驻留 + 磁盘回读）
- `on_demand_cache_mb`（1024）、`on_demand_prefetch_frames`（20）、`on_demand_io_timeout_ms`（800）
- `local_ivox_window_enable` / `local_ivox_radius`(10) / `local_ivox_interval`(5) / `local_ivox_fallback`(15)
- 关闭全部即回到"旧全量加载"行为（P0/P3/P3b 均为旁路分支，回退零残留）

**前端（App 插件 `navigation-mapping`）**
- `use_tile_basemap`（默认关）：开静态瓦片底图（并停用旧全量静态订阅/渲染）
- `force_legacy_static_map`（调试）：强制旧全量渲染
- 无 chunks 时自动回退旧全量并一次性提示

**后端接口（`extra.py`）**
- `get_map_chunks` / `get_levels` / `get_map_l2` / `get_chunk_fragments` / `get_keyframe_poses`
- `tiles_blueprint`：`/tiles/<map>/<gx_gy>/<lod>.pcd`
- 注意：插件代理只回传 JSON（二进制 502），瓦片/预览由插件**直连机器人 :9000**（后端已开 CORS）
