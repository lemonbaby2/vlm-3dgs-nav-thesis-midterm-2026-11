## 1. 背景与现状（代码级）

### 1.1 内存增长清单（建图模式）

| 容器/对象 | 内容 | 坐标系 | 规模 | 有界？ |
|---|---|---|---|---|
| `surf_CloudKeyFrames_imu` | 关键帧面点云 `PointXYZINormal` | imu | 每帧最大，主风险 | ❌ |
| `ground_CloudKeyFrames_lidar_` | 地面点云 `PointXYZI` | base | 每帧 ~6.5KB | ❌ |
| `noground_CloudKeyFrames_lidar_` | 障碍点云 `PointXYZI` | base | 每帧 ~48KB | ❌ |
| `ground_CloudKeyFrames_valid_` | 每帧地面有效标志 | — | 字节级 | ❌（可忽略） |
| `cloudKeyPoses3D/6D_imu(_correct)`、`keyframe_pose_6d_` 等 | 位姿 | — | K 级 | ❌（很小） |
| GTSAM 因子图 | 位姿约束 | — | K 级 | ❌（较小） |
| IVox `ivox_map_` | 局部匹配索引 | map | 40000 体素 LRU + 50 点/体素 | ✅ |
| `MapIncremental` 在线轨迹 | 帧间增量点 | map | TTL 清理 | ✅ |

**结论：无界增长的是关键帧点云容器（尤其 surf），这是爆内存的唯一主因。**

> 读表说明：**✅ = 有界（自带上限，不用改造）；❌ = 无界（本次改造对象）**。`IVox`（40000 体素 LRU + 50 点/体素）和 `MapIncremental`（TTL 清理）虽然每帧都在写，但**已经自带天花板**，不是爆内存的原因；只有关键帧点云容器（surf/ground/obs）会随里程一路涨。

### 1.2 现有落盘路径（唯一入口）

- 服务入口：`save_map`（`laser_mapping.cc:6889-6891`，调 `savemap_to_dir`）
- 快照：`:10926-10948`，`mtx` 下拷贝容器（**只拷 shared_ptr 向量，不复制点云本体**）
- 事务：先写 `<map>.saving/` 暂存目录（`:10920-10924`），完成后 rename 为正式目录、旧图转 `<map>.backup`
- 每帧写盘：`surf/ground/obs/<i>.pcd`，`savePCDFileBinary`（`:11202-11214`）
- 位姿与标志：`poses_base.txt` / `poses_lidar.txt` / `poses_localization.txt`（raw imu）/ `poses_gps_*.txt` / `ground_valid.txt`（`:11236-11298`）
- 派生图：`global_map.pcd` / `global_ground_map.pcd`（含 `FillGroundCloudHoles` 补洞，`:11231-11233`）/ `*_downsize.pcd`
- 索引/元数据：`keyframe_index.json`（`WriteKeyframeIndexJson:1348`）、`map_block_meta.json`（`WriteMapBlockMetaJson:1440`）、`global_index/id_allocator.json`（`ResolveGlobalKeyframeIds:1323`）
- **建图过程中没有任何周期写盘**

### 1.3 三个关键观察（方案成立的前提）

1. **点云局部坐标系直存**：`surf/<i>.pcd` 存 imu 系、`ground/obs/<i>.pcd` 存 base 系；全局位姿在单独的文本文件里。闭环优化只会改位姿 → **点云文件一次写入、永不重写**
2. **位姿文件是纯文本、体量极小**（170 帧 ≈ 8.5KB）：可以全量重写，不需要复杂的增量日志
3. **ground/obs 容器在建图期间几乎只被暂存**（除保存快照 `:10945-10946`、`:11618` 外无消费者）→ 落盘后**可以最早释放**；surf 有 4~5 处运行期消费者（见附录 11.1），需要读盘回退

### 1.4 与 260827 Spec、主题二的边界

- 本主题只改**写路径 + 内存管理**，不改加载/匹配逻辑；与"删除启动全局 IVox / 滑动窗口 / 删 loaded_map"（`x_slam_局部IVox按需构建与滑动窗口改造Spec.md`）互不冲突，可并行
- 显示地图（`visualizeGlobalmap`）在滑窗释放后若仍需内存容器，走 Provider 读盘（有上限），最终由主题二的 downsize/瓦片替代

## 2. 设计目标与不变量

### 2.1 目标

1. 建图内存有上限：滑窗外的已落盘帧从内存释放
2. 任意时刻断电：最多丢尾部 `flush_interval` 帧以内，已落盘部分可恢复/可最终化
3. 最终保存（finalize）只做三件事：补尾部、重写位姿、后台烘焙派生图
4. 开关关闭时，行为、产物与现状**完全一致**

### 2.2 不变量（评审重点）

- **点云文件写一次**：`surf/ground/obs/<i>.pcd` 一旦落盘，永不被重写
- **位姿可重写**：位姿文件允许全量重写，必须带 `pose_version`
- **先文件后游标**：任何"帧已落盘"的声明（游标推进）必须在对应文件 fsync 之后
- **单帧原子**：单文件 `tmp + rename`，不存在"半帧"被读取
- **游标语义（易错点）**：`flushed_keyframe_count` 是**本工地会话相对计数**；工地起始绝对帧号由 `first_keyframe_index` 锚定（保存后续建 >0）。任何把游标与"容器绝对帧号"比较的代码（如 P1 释放器）必须先换算 `绝对已落盘 = first_keyframe_index + flushed`——2026-10-13 实机踩过此坑（见 §11.3 A7）
- **保护窗不变量（P2）**：可释放 ⟺ 保护窗外 ∧ 已落盘（绝对帧号）；保护窗 ⊇ 匹配重建半径 + 余量，窗内帧必然常驻
- **Provider 契约（P2）**：禁止持 `mtx` 调 `Get`；读盘失败绝不改动容器状态；返回 `shared_ptr` 期间内存不被释放（引用计数保护）
- **开关可回退**：`realtime_store_enable=false` 时进入原 `savemap_to_dir` 流程，零差异

## 4. 详细设计

### 4.1 存储目录与生命周期

**大白话**：建图时文件先写进一个"工地"（`.building`），**别人不许进去用**；等保存验收合格，才改名成正式地图。这样"半成品"永远不会被当成成品加载。

**工地目录结构**：

```
<nav_root>/
  <map_name>.building/          ← 建图期实时写入（本主题新增）
    surf/ ground/ obs/          ← 每关键帧文件（与正式格式完全一致）
    poses_base.txt poses_lidar.txt poses_localization.txt
    poses_gps_*.txt ground_valid.txt
    keyframe_index.json map_block_meta.json
    store_state.json            ← 本主题新增：游标/版本/会话/块
    chunks/                     ← 瓦片产物（§4.14，finalize/CLI 生成）：
      index.json                ←   分块清单（增量更新）
      <gx>_<gy>/lod1.pcd        ←   每块降采样
      <gx>_<gy>/fragments.json  ←   可选：patch 切片索引
    stairs/                     ← 在线语义草稿（§4.13，P3）：
      stair_patches.draft.yaml  ←   reviewed=false 草稿
      stair_graph.draft.yaml
    ground_levels.draft.json    ← 在线楼层带草稿
    nav_light/                  ← 全局粗图（§4.15）：
      index.json
      floors/<id>/grid.bin  meta.json  topology.json
  <map_name>.saving/            ← 旧事务暂存（保留兼容）
  <map_name>/                   ← 正式地图（finalize 后的权威产物）
```

**三个状态与规则**：

| 状态 | 目录 | 谁能用 |
|---|---|---|
| `building`（施工中） | `<map_name>.building/` | **只许建图进程读写**；地图列表、跨图扫描、planner 加载一律看不见 |
| `finalizing`（收尾中） | 同上（`state=finalizing`） | 排空写队列、补尾部、重写位姿/索引 |
| `finalized`（交房） | `<map_name>/`（rename 而来） | 所有消费者（加载/规划/前端） |

- **finalize（验收）**：排空写队列 → 补写尾部 → 重写位姿/索引 → 构建派生图（或后台）→ `rename(.building → 正式目录)`；若正式目录已存在，按旧逻辑转 `.backup`
- **崩溃后（工地还在）**：两条出路——**恢复继续建**（P4 resume）或**直接 finalize 成部分地图**
- **开关关闭**：不创建 `.building`，完全走旧流程

> 待定（B1）：目录过滤要排查所有"会扫地图目录"的地方（地图列表、跨图扫描 `FindInterMapLoopCandidate:1069-1113`、planner 加载、部署脚本），确保 `*.building/*.saving/*.backup` 一律跳过。

### 4.2 写路径 Hook（关键帧定稿时"上报"）

**大白话**：不新造流程，只在"关键帧定稿"的现有函数末尾挂一个"上报"动作——**数据在内存里装完整了，才交给写线程**。

**挂在哪**（两处关键帧定稿函数末尾、容器 push_back 全部完成之后）：

| 函数 | 位置 | 说明 |
|---|---|---|
| `addKeyframe` | `laser_mapping.cc:12774`，push_back 在 `:12743-12745` | 建图模式新关键帧 |
| `addRelocalizationKeyframe` | `:12621`，push_back 在 `:12945-12947` | 重定位 handoff 插入的关键帧 |

**上报做什么**：

```
MapStore::OnKeyframeCommitted(uint32_t index)：
  if (!enable || !building) return;   // 开关关闭/不在工地 → 什么都不做
  AsyncWriter::Enqueue({index, surf[i], ground[i], obs[i],
                        ground_valid[i], pose_snapshot(i), pose_version});
```

**两条纪律**：
1. **入队快照在 `mtx` 下取 shared_ptr**（与 savemap 快照同规则）→ 入队后点云不可变，写线程随便读
2. **index 必须连续**：不连续说明有帧没走定稿流程 → 报错并禁止推进游标（游标语义="连续前缀"）

### 4.3 异步写线程与队列（专职"抄写员"）

**大白话**：建图主线程只管算，另设一个专职"抄写员"后台写盘——**绝不在雷达/定位线程里写文件**。

**基本设定**：

| 项 | 设计 | 为什么 |
|---|---|---|
| 线程 | 单写线程 + 有界队列（`realtime_store_queue_max`=200） | 单线程顺序写、好限速、无并发复杂度 |
| 单帧写 | 3 个 pcd 各 `tmp + rename` | 原子：读不到"半个文件" |
| fsync | 不逐帧刷；每 `fsync_batch`=20 帧批量刷 | 实测每批 fsync 仅 24ms（§11.3 A2），刷太勤没意义还费盘 |
| 限速 | `realtime_store_max_bytes_per_sec`=150MB/s | 实测 NVMe 写 850MB/s+；限速是防"和别的任务抢带宽"，不是怕压垮盘 |
| 优先级 | 低于雷达/定位线程 | 建图实时性优先 |

**队列满了怎么办（背压三级）**：
1. 暂停内存释放（窗口临时变大）——**优先保数据**
2. 队列仍满 → 短暂阻塞入队并告警——宁可卡一下，**绝不丢帧**
3. 写线程出错（磁盘满/IO 错）→ 降级：停止释放、置错误标志、通知 web 状态

**为什么"不丢帧"是底线**：关键帧是**唯一一次写盘机会**（点云局部坐标系直存、闭环也不重写点云），丢了就真没了。

### 4.4 落盘内容与顺序（每次 flush 的"作业顺序"）

**大白话**：先写大件（点云文件）→ 刷到盘上 → 再抄小本子（位姿/标志）→ 更新户口本（索引）→ **最后才挪动进度条（游标）**。顺序不能乱。

**固定顺序（为什么这么排）**：

| 步 | 动作 | 为什么 |
|---|---|---|
| 1 | 写未落盘的 pcd（按 index 升序，逐个 `tmp+rename`） | 大件先落，单帧原子 |
| 2 | 批量 fsync | 确认真到盘上 |
| 3 | 全量重写 `poses_*.txt` / `ground_valid.txt` | 小文件（约 8.5KB/170 帧），重写简单且天然幂等 |
| 4 | 刷新 `keyframe_index.json` / `map_block_meta.json` | 索引与位姿同步 |
| 5 | 更新 `store_state.json`（游标） | **最后一步**：游标推进 = 前面全部成功的"声明" |

- **位姿为什么全量重写**：闭环后位姿会变，全量覆盖天然幂等；追加+修补反而复杂
- **位姿来源与 savemap 一致**：raw imu → `poses_localization.txt`；base/lidar 由外参换算（`:11170-11176`）

### 4.5 `store_state.json`（工地门口的"施工进度板"）

**大白话**：一个小文件，记录"这工地现在什么状态、写到第几帧、版本几"——**断电恢复全靠它**。

**字段说明**：

| 字段 | 含义 | 用途 |
|---|---|---|
| `version` | 进度板格式版本 | 兼容 |
| `map_id` | 图名 | 防串工地 |
| `session_id` | 本次建图会话 id | 追溯/续建 |
| `state` | building / finalizing / finalized / recovering | 生命周期 |
| `flushed_keyframe_count` | **已落盘并 fsync 的连续帧数（游标）** | 恢复的基准 |
| `pose_version` | 与 `keyframe_index`/`map_block_meta` 对齐 | 闭环后递增 |
| `chunk_id` / `chunk_start_frame` | 当前分块 | 分块密封（§4.8） |
| `keyframe_index_flushed_at` | 索引刷到第几帧 | 双游标（D1） |
| `derived_map_dirty` | 派生图是否需重烘焙 | finalize/后台 |
| `updated_at` | 更新时间 | 运维 |

```json
{
  "version": 1,
  "map_id": "cf09301",
  "session_id": "20261010-141530",
  "state": "building",
  "flushed_keyframe_count": 170,
  "pose_version": 3,
  "chunk_id": 0,
  "chunk_start_frame": 0,
  "keyframe_index_flushed_at": 170,
  "derived_map_dirty": true,
  "updated_at": "2026-10-10T14:20:31"
}
```

**纪律**：它永远是 flush 序列的**最后一步写**——它说"第 N 帧好了"，前面 N 帧一定都真在盘上。

### 4.6 内存滑窗与 KeyframeCloudProvider

**总原则（三句话）**：边建边存（磁盘有备份）→ 内存只留"热数据"→ 装不下就换出去（磁盘 + 按需读回 + 缓存上限）。

#### 4.6.1 窗口设计：按"帧数 ∪ 距离"，不按钟表时间

```
keep = max(最近 M 帧, 距离 R 米内的帧)
```

- **不按时间**：机器人走走停停，"最近 30 秒"与数据量/位置不挂钩，算不准
- **M 帧（建议 200）**：管"原地徘徊、反复重定位"——没走路也得留够帧
- **R 米（建议 30m；P1 ground/obs 放宽为 15m）**：管"快速直线跑"——跑得快时距离才靠得住
- 参数已按 robot-3011 实测定型（0.31MB/帧 → 200 帧 ≈ 62MB，见 11.3 A1）
- **P1 ground/obs 的放宽**：ground/obs 不参与实时匹配（唯一消费者是保存快照，且已改磁盘回读），因此释放条件放宽为
  `已落盘 且（超出 M=200 帧 或 离当前位置 > R=15m）`，并保底最近 20 帧；这样"走十几米"即可验证释放行为（2026-10-13 调参）。surf（P2）仍按 `keep = max(M 帧, R 米)` 保守保护。

#### 4.6.2 永不释放的保护帧（硬约束）

1. **当前匹配窗口内的帧**：IVox 滑动窗口（10m）+ 邻域余量（5m，`surroundingKeyframeSearchRadius`）——扔了匹配就缺帧
2. **尚未 fsync 的帧**：写盘积压时窗口自动变大——**宁可多占内存，也不丢数据、不卡匹配**
3. **回环/显示正在用的帧**：回环通过 Provider 读盘（实测单帧 0.4ms），不要求常驻；显示 P2 后改走 downsize/瓦片，不再保护

#### 4.6.3 释放顺序与节奏（先易后难）

> **三个点云盒子（surf/ground/obs）共用同一套窗口（§4.6.1）**，区别只在释放优先级与保护条件：ground/obs 落盘后即可扔（约 37% 收益、几乎零风险，P1）；surf 需保留匹配窗口内的帧、且消费者改走 Provider（约 63% 收益，P2）。

| 阶段 | 释放对象 | 前提 | 运行期影响的消费者 |
|---|---|---|---|
| P1 | `ground`/`obs`（已落盘 且（>200 帧 或 >15m），最近 20 帧保底） | 帧已 fsync | 只有保存快照（保存时对已释放帧走磁盘回读，天然满足） |
| P2 | `surf`（超出窗口的已落盘帧） | 帧已 fsync | 5 处消费者（附录 11.1），全部改走 Provider |

- **节奏**：每个关键帧检查一次（条件：已落盘且超窗；实现为 O(1) 摊销扫描，与 flush 并行无锁竞争）
- **前置**：释放前必须确认对应帧已 fsync（先文件后游标，见 §2.2 不变量）

#### 4.6.4 三级水位（装不下就自动缩窗）

| 水位（相对预算） | 动作 |
|---|---|
| 绿色（< 70%） | 正常：窗口按 M=200 / R=15m 运行（P1 ground/obs） |
| 黄色（70~90%） | 窗口缩到下限、暂停预取、加快淘汰最老帧 |
| 红色（> 90%） | 只保"匹配必需"的最小窗口、LRU 清零、写盘队列优先排空；仍高 → 告警提示尽快保存 |

**与写盘进度联动**：水位评估中"已落盘"是硬条件——写盘落后时窗口只增不减（数据安全优先于内存占用）。

#### 4.6.7 Provider 设计（窗口外的取件员，P2）

**目标**：窗口外已释放的关键帧点云（P2：surf；ground/obs 已由 P1 覆盖）在不阻塞跟踪的前提下按需恢复：内存命中直取、未命中读盘（**工地目录 → 旧官方图目录**，与 P1 回读同链）、装载后进入 LRU 缓存。

**三层存储模型**：

| 层 | 内容 | 容量 | 说明 |
|---|---|---|---|
| 保护窗（常驻） | 最近 M 帧 ∪ R 米内的帧 | 定量（见参数） | 永不释放；⊇ 匹配重建半径（`surroundingKeyframeSearchRadius` 5m）+ 余量 |
| LRU 缓存 | 按需从磁盘装载的历史帧 | `realtime_store_cache_mb`（起步 1024MB，A1 实测定型） | 预算内 LRU 淘汰 |
| 磁盘 | `<layer>/<i>.pcd`（写一次不重写） | 磁盘容量 | 只读；工地/官方图两级 |

**API 草案（C++ 新模块 `keyframe_cloud_provider.h/cc`，沿用 map_store 的风格）**：

```cpp
class KeyframeCloudProvider {
public:
  using SurfPtr = pcl::PointCloud<pcl::PointXYZINormal>::Ptr;
  using XyziPtr = pcl::PointCloud<pcl::PointXYZI>::Ptr;

  void Bind(std::vector<SurfPtr>* surf);       // 容器地址（LaserMapping 持有，槽位制）
  void SetMapDirs(std::string building_dir, std::string official_dir);
  SurfPtr GetSurf(int idx);                     // 命中→直返；未命中→读盘插回；失败→nullptr
  XyziPtr GetLayer(const char* layer, int idx); // ground/obs（显示重建等备用）
  bool IsPinned(int idx) const;                 // 释放器协作：缓存/使用中，本次跳过
  ProviderStats stats() const;                  // hits/misses/read p50/p95/evicted
};
```

- **装载顺序**：槽位非空 → 直返（热路径，短暂加锁）；否则读盘：工地目录（`idx ≥ 当前工地首帧`）→ 官方图目录；读到后**原子插回槽位**（锁内判重，已有则用已有）。读盘失败：返回 nullptr + 限流告警，**不改动容器状态**
- **与释放器的分工**：释放器/淘汰共用一把尺子——`可置空 ⟺ 保护窗外 ∧ 已落盘（绝对帧号）`；**LRU 预算淘汰只回收记账（被淘汰帧恢复"可释放"），实际置空统一由释放器扫描执行**（Provider 不感知保护窗，避免越权置空）；**LRU 钉住的帧不释放**
- **引用计数保护（连锁安全）**：Provider 返回 `shared_ptr`；使用期间引用计数 >0，释放/LRU 只把帧"移出容器"，内存不析构；用完即回收——回环/显示无需额外保护标记（§11.4.2）

**线程安全契约（实现红线）**：

1. 容器仍由现有 `mtx` 保护；Provider 内部 LRU/计数用独立 `provider_mutex_`；锁序固定 `mtx → provider_mutex_`（禁止反向嵌套）
2. **禁止持 `mtx` 调 `Get`**（Get 内部要取 `mtx`）：消费者统一改为"**先快照位姿（锁内）→ 再逐索引取帧（锁外）→ 变换/降采样（锁外）**"
3. 保护窗内帧必然常驻（不变量）→ 热路径（周期重建 IVox）Get 全部命中内存；读盘只出现在冷路径（回环历史子图、handoff、保存回读、显示后台重建）

**消费者改造规则**（完整清单见 §11.1；工作区当前行号）：

| 消费者 | 改造要点 | 预期读盘 |
|---|---|---|
| `recontructIKdTree`(:7801) / `recontructIKdTree_now`(:7944/:7960) / handoff(:6654-6696) | 锁内用 **`GetSurfLocked`（仅内存直取，不读盘）**——保护窗内帧必然常驻，等价于原语义；**缺帧（不应发生）→ 登记 `surf_pending_reload_` 并放弃本次重建（保留旧 IVox）**，回环线程周期补载后下一轮重建完成（已按此实现，无需扩大锁外范围） | 0（窗内常驻；补载在回环线程） |
| `loopFindNearKeyframes`(:12077，调用点 :8733/:8762/:8769) | 逐索引 `GetSurf`（当前 1 帧 + 历史 `historyKeyframeSearchNum`×2≈21 帧）；点数门槛（300/1000）不变，缺帧走现有"跳过本轮" | ≤22 帧/次（冷 ≈9ms） |
| `savemap_to_dir`(:10835+，surf 快照 :10993) | surf 快照空（已释放）→ 与 P1 同链回读 `surf/<i>.pcd`（PointXYZINormal）；缺失则**拒绝保存** | 全量一次性 |
| `visualizeGlobalmap`(:11635) | 见下"显示改道" | 后台限速 |
| `load_map`(:13226，定位模式) | **不在 P2 范围**：定位模式不释放（`slam_mode_ != 0` 早退），保持全量装载现状 | — |

**显示改道（对应任务 P2-5，主题二瓦片上线前的过渡）**：现显示每次在 600m 半径内全量变换数万帧——若直接接 Provider 会把已释放帧每周期重读一遍（打盘）。改为**增量累积显示云**（已实现）：

- 触发条件：`realtime_store_enable && realtime_store_release_surf`（默认关时完全走原路径，零行为变化；loop 线程 1Hz 持续追赶，get_map 时发布）
- 追赶机制：每次调用增量处理新帧（**常规预算 200 帧/周期；从头重建 2000 帧/周期**），按 200 帧分块变换→体素（显示 leaf，默认 0.3m）→并入累积云；已释放的 surf 帧经 Provider 读盘
- 重建触发（`display_accum_dirty_`）：全局位姿修正后、`load_map` 后、`clear_map` 后；重建期间发布旧累积（to-be：双缓冲渐进，当前为清空后逐步恢复）
- ground 采用"驻留帧"策略（1Hz 追赶下总新鲜；重建积压中已释放帧跳过，不劣于 P1 现状）
- 发布路径不变（`/x_nav/global_map`、`/x_nav/global_ground`）

**失败降级矩阵**：

| 场景 | 行为 |
|---|---|
| 单帧读盘/解码失败 | 返回 nullptr；限流告警；消费者按"缺帧"处理（回环跳轮、重建放弃、保存拒绝、显示跳过） |
| 工地+官方目录均无该帧 | 同上；计入 `provider_miss_total`（健康度） |
| 冷路径读盘变慢 | 打点记录（p50/p95）；同步读仍在调用线程，只影响该次冷路径耗时，不加超时强杀 |

**参数（新增，默认关）**：

| 参数 | 默认 | 说明 |
|---|---|---|
| `realtime_store_release_surf` | `false` | surf 释放开关（灰度放开） |
| `realtime_store_surf_window_frames` | `500` | surf 保护窗帧数（比 ground/obs 保守；覆盖原地徘徊/重定位） |
| `realtime_store_surf_window_radius_m` | `30` | surf 保护窗半径（⊇ 匹配重建 5m + 余量；A1 建议 ≥30m） |
| `realtime_store_cache_mb` | `1024` | Provider LRU 预算 |

**指标（并入现有 30s 周期日志）**：保护窗 retained/总数、cache 帧数/MB、provider hits/misses、read p50/p95、released_surf。

### 4.7 索引与元数据刷新策略（户口本 + 状态便签）

**大白话**：`keyframe_index.json` 是地图的"**户口本**"（每帧位姿/文件/编号），`map_block_meta.json` 是"**状态便签**"（哪块脏了要重算）。

- **户口本**：每 flush 或每 `index_flush_frames`=50 帧全量重写（74KB/170 帧，成本可接受）；**闭环后必须立即重写**（位姿变了）
- **状态便签**（与户口本同步）：
  | 字段 | 含义 | 何时置位/清除 |
  |---|---|---|
  | `pose_dirty` | 闭环/优化改过位姿 | 优化后置位；位姿重写后清除 |
  | `index_dirty` | 索引待刷 | 刷完清除 |
  | `derived_map_dirty` | 派生图（global_map/瓦片/粗图）待重烘焙 | 位姿变化后置位；烘焙后清除 |
- **全局帧号**：建图开始时一次性分配（`ResolveGlobalKeyframeIds:1323-1346`，resume 时从已有分配器续接），保证跨图不撞号

### 4.8 分块密封（chunk seal，P2/P3）

**大白话**：像写书——每攒够一章就"装订"一次：强制刷盘、刷新索引、推进块号。装订点同时也是"清内存 / 触发后台烘焙"的**安全检查点**。

- **触发**：每 `chunk_frames`=500 帧 或 `chunk_meters`=100m（先到先算）
- **动作**：① 强制 fsync 当前批 → ② 刷新索引/元数据 → ③ 推进 `chunk_id`，更新分块索引（格式见主题二附录 D）
- 与主题一瓦片、主题二分块产物**共用同一分块协议**，不重复造

### 4.9 崩溃恢复流程（P3）：停电后的"复工检查"

**大白话**：按进度板清点——数到第 N 帧都是完好的，后面的半截文件拆掉，从 N 继续。

启动或 resume 时检测 `<map>.building/store_state.json`：

1. 读取 `flushed_keyframe_count = N`
2. 校验 `surf/ground/obs/0..N-1.pcd` 存在且可解析；缺任何一帧 → 以**最小连续前缀**为准修正 N
3. 校验位姿文件行数 ≥ N；多余行截断到 N
4. 删除 N 之后的半写文件（`*.tmp` 与孤立 `<i>.pcd`）
5. 状态置 `recovering` → 刷新索引 → 回到 `building`
6. 两条出口：**继续建图**（P4 resume）或**直接 finalize**（产出部分地图）

**两道保险**：
- 单文件 `tmp+rename` → 永远读不到"半帧"
- 进度板最后写 → 进度板说"好了"的，一定都真在盘上

### 4.10 派生图烘焙（finalize）：把大图拼出来

**大白话**：保存时用**磁盘上的关键帧**拼出全图（global_map / ground / downsize）——只读盘、不依赖内存容器。

- **流程**：
  - `surf/<i>.pcd` + 位姿 → 变换拼接 → `global_map.pcd`（XYZI）
  - `ground/<i>.pcd`（仅 valid 帧）+ 位姿 → `global_ground_map.pcd` → 补洞 `FillGroundCloudHoles`（`:11231-11233`）
  - 各自 VoxelGrid 0.3m → `*_downsize.pcd`
- **流式实现**：逐帧读→变换→追加→释放；峰值内存 = 单帧 + 目标云
- **实测（robot-3011，cf09301）**：全流程 **0.68s**、峰值 **68MB** → 同步烘焙无压力；10× 图 ≈7s、50× 图 ≈35s，大图再考虑后台化（§11.3 A4）
- **闭环后过期**：`derived_map_dirty=true` → finalize 或后台重烘焙

### 4.11 与旧 `save_map` 的关系（开关=选新老流程）

**大白话**：新流程（工地 + finalize）和老流程（结尾一把写）二选一，由开关控制；**关掉=与现在完全一样**。

- `save_map` 保留不动：开关关闭零差异；开关开启时等价于触发 finalize（同一输出目录/事务语义）
- 未 finalize 的 `.building` 目录**不参与**多图扫描 / 地图列表 / planner 加载（目录过滤，见 §4.1）
- Web 层 `save_map`/`switch_map`/地图列表接口行为不变；可选新增 `flush_map`（只刷游标、不 finalize）

### 4.12 open/resume 接口预留（为主题三"二次建图"）

**大白话**：给"把工地重新打开继续干"留好接口——读进度板、校验、从上次断点接着写。

- `MapStore::OpenExisting(<map>.building 或正式目录, continue_session=true)`：
  - 读 `store_state.json` → 校验 → 从 `flushed_keyframe_count` 继续写
  - 容器先装载"窗口内帧"（读盘），位姿索引全量装载
- P4 才接线到"续建模式"（配合重定位），但 **P0 起按此接口设计，避免返工**

### 4.13 在线语义草稿（patch / 楼层，C++）

**现状**：patch/楼层是**保存后**由 Python 工具链生成（`stair_draft.py` + `stair_map.py`，web 层 `extra.py:703` 异步触发）；在线只有 `stair_surface_segmenter` 分割候选与 `floor_anchor` 楼层锚定，**没有在线 patch**。

**目标**：C++ 化 + 在线草稿 + finalize 权威定稿。

**为什么值得在线（与瓦片对比）**：patch 草稿是"**小、便宜、直击痛点**"——事件驱动（爬完一部楼梯才跑一次）、几百毫秒、写几 KB；价值是"**当场发现楼梯不合格、当场补爬**"（cf09301 的教训正是保存后才发现）。瓦片则是"大工程换小收益"——它是加载侧产物，**已取消在线切割**（§4.14，改为 finalize/CLI 生成）。**前提**：协同建图（现场有人可补救）；无人值守时其价值降级为远程监控/日志。

```
C++ 模块（x_nav 工程内新增 stair_patch_builder.{h,cpp}）：
  与现有 Python 算法一对一翻译，质检常量/阈值保持一致：
    · 轨迹爬升段检测（z 单调、水平距离、爬升阈值）
    · ROI / pass 中线 / 逐级锚点
    · 点云测宽（z±0.05 投影 + 横向聚类 80 分位）
    · 质检门控（级数连续/宽度/级高/覆盖率/轨迹偏置）
  复用 planner 的 C++ 语义结构（semantic_map.hpp 的解析与结构体），
  新增一个小的 YAML 写入器保证 schema 与现有完全一致；
  配套 gtest 单测（与导航代码同一套测试体系）。
```

**在线流水线（SemanticPipeline，事件驱动，后台低优先级）**：

```
关键帧落盘（借 flush 游标，只读已 flush 帧）→ 轨迹缓冲
  → 检测爬升（Δz ≥ realtime_semantic_climb_dz_m 且单调）
  → 爬升完成 / 每 N 帧 → 生成草稿：
       铺锚点 + 用已落盘点云测宽（能测多少测多少）
       写 stairs/stair_patches.draft.yaml + stair_graph.draft.yaml（reviewed=false）
  → 楼层带：ground 云 z 直方图增量更新
       写 ground_levels.draft.json（与 floor_anchor 高度源对齐）
触发频率：只在过楼梯时触发几次；绝不在 Run 线程执行
```

**draft 约定与版本**：

- 草稿只写 `*.draft.*`；正式 `stairs/`、`ground_levels.json` 只由 finalize 产出
- 草稿仅供 **UI/预览**；planner 不消费（`reviewed` 门控天然挡住）
- 草稿绑定 `pose_version`；闭环/位姿变化 → 标脏重算或直接丢弃（重算秒级）

**finalize 交接**：权威重算（完整轨迹 + 全量点云 + 质检门控）→ 写正式产物；草稿清理。
**旧图补算**：C++ CLI `semantic_tool rebake --map-dir ...`（替代 Python 离线调用）。

**`reviewed` 的产生方式（口径统一）**：

- **自动几何门**：`validate_and_gate` 的十几项检查（级数连续/宽度/级高/覆盖率/轨迹偏置）在 C++ 化时一并翻译，作为**建议/预警**
- **放行策略可配置**：CLI/工具默认"自动门过即 `reviewed=true`"；**线上保存路径稳妥起见强制 `reviewed=false`**，等人工/抽查后放行
- 现场看到的"全部 rejected 归档"（如 cf09301）是**放行策略的保守选择**，不是"没有自动化"
- planner 侧门槛不变：`require_reviewed=true` 时只采用 `reviewed=true` 的语义

**收益**：建图中即可看到楼层/楼梯；爬完楼梯当场发现质量问题（cf09301 教训）；finalize 减负。

> 瓦片产物的字段/命名/格式**规范统一见主题二附录 D**；本节只讲"生成时机与流程、patch 切片"。
>
> **定位**：瓦片是**加载侧产物**，建图过程本身不需要它。生成只有两条路：**finalize 烘焙（主路径）+ 旧图 CLI 补算**；不做在线切割（实测 finalize 全量烘焙仅 0.68s，§11.3 A4，没必要为它引入常驻累加器/批写/在线脏块管理）。

**生成流程（finalize 烘焙，从磁盘流式做）**：

```
读全部关键帧位姿 + surf/<i>.pcd（磁盘流式）
  → 按位姿归属瓦片 floor(x/chunk_size), floor(y/chunk_size)
  → 逐帧降采样（0.3m）并入对应瓦片（内存只保活跃瓦片）
  → 每块写 chunks/<gx>_<gy>/lod1.pcd（tmp+rename）
  → 汇总 chunks/index.json（关键帧列表、bbox、z_range、floors、version）
finalize 校验：索引覆盖全部关键帧、版本与 keyframe_index 一致
```

- **旧图/重烘焙**：C++ CLI `semantic_tool tile`；合并/编辑后由统一重烘焙流水线重算（主题三 §4.3）
- **多层同块**：二维切块切不开竖直方向 → 瓦片元数据必须带 `z_range/floors`（与 levels/patch 配合做二级切分）
- **版本**：瓦片绑 `source_pose_version`；版本不一致 → 消费者忽略缓存

**patch 切片（红线：语义主表不切碎）**：

| 表 | 内容 | 角色 |
|---|---|---|
| **patch（语义主表，现有不动）** | 完整面片 ID / bbox / mean_z / 楼层归属 / 图边 | 规划、逐边执行、质检的**权威** |
| **patch_fragment（新增，可选）** | `frag_id / parent_patch_id / tile_id / bbox∩瓦片 / floor_id / z / type / reviewed(继承)` | 加载/显示/索引挂接 |

- 切片只是"目录"：每个 fragment 指回 parent;语义永远认 parent（避免图边碎片化、逐踏面执行混乱）
- 生成：**finalize 烘焙时顺带生成**；也可**不落盘**，加载时按 bbox∩瓦片查询式现算（**待拍板**，见 11.3 C2）
- 用途：瓦片↔语义挂接（加载某块即知其楼层/面片）、前端按层显示、点楼梯高亮跨块、planner 语义感知预取

### 4.15 全局轻量层（nav_light）与全局规划最小依赖

**大白话**：粗图就是一张"**这栋楼哪里能走的示意图**"——每层一张、0.5m 一格、每格 1 个字节（自由/障碍/未知/楼梯）。**它是文件产物，不是运行时现算**：保存时烘焙好，planner 启动只读它，不用碰点云。

**nav_light 文件结构**：

```
<map>/nav_light/
  index.json                 ← 版本、分辨率、各层清单
  floors/<id>/grid.bin       ← 每层粗图，1 字节/格（0 自由 / 1 障碍 / 2 未知 / 3 楼梯）
  floors/<id>/meta.json      ← 原点、分辨率、尺寸、层高
  floors/<id>/topology.json  ← 可选：拓扑节点/边
```

**粗图生成五步**（同一套算法三种场合复用）：

```
① 定分辨率（0.5m，可调）与坐标原点
② 按 ground_levels 分层（每层一张图）
③ 逐格判状态：地面带有点且障碍带无点 → 自由；障碍带有点 → 障碍；
             无数据 → 未知；落在 tread/entry/exit patch → 楼梯
④ 障碍膨胀（机器人半径）+ 净空近似（到最近障碍的格数）
⑤ 落盘 grid.bin + meta.json
```

- **保守原则**：未知按不可通行；膨胀宁多不少；粗图说能走、细图发现是墙 → 局部修正/重规划
- **生成时机**：**finalize 烘焙（主路径）+ 旧图 CLI `semantic_tool bake-nav`**；合并/编辑后统一重烘焙（不做在线聚合）
- **大小**：100m×100m/层 ≈ 4 万格 ≈ 40KB；10 层 ≈ 400KB（可调 0.5~1m）
- **跨层不物理连**：每层一张图；跨层由 patch 语义图衔接（entry → treads → exit，见主题六附录 E）

**全局规划必须加载的最小集合**（其余按需）：

| # | 事项 | 体量 |
|---|---|---|
| 1 | 每层粗图 / 拓扑 | MB 级 |
| 2 | patch 语义图（patches + graph） | 几十 KB |
| 3 | `ground_levels` 楼层 | KB 级 |
| 4 | `nav_points` 导航点 | KB 级 |
| 5 | `pose_version`（一致性校验） | 字节 |

- **明确不需要**：`global_map.pcd` 全量、全图 SDF/KD 树、全图关键帧
- **按需加载**：沿走廊瓦片 lod1/lod0、区域 Vox/SDF、实时点云（局部执行依赖）
- 运行方式与里程碑见主题六（planner 启动只读 nav_light → 全局规划 → 区域瓦片按需）

### 4.16 建图在线可用性评估（"这图能不能用"）

**大白话**：像边走边给地图做"**体检报告**"——盯四个指标（定位能不能定、导航能不能走、跨层能不能上、语义可不可信），出红黄就当场提醒，而不是保存后才发现问题（cf09301 楼梯教训）。

**目标**：建图中自动给出可用性判断（预警级）。

**四类判据与现有信号**：

| 类别 | 判据 | 现有信号/组件 |
|---|---|---|
| 定位可用 | 关键帧密度（每 100m² 帧数）、surf 点数/帧、地面覆盖率、漂移/闭环状态 | GICP score、`mapping_drift_diag_*`、回环计数 |
| 导航可用 | 地面格覆盖率、缺口率、稀疏区、窄道净空 | `ground_valid` 逐帧统计、`ground_seg_stats_` |
| 跨层可用 | 楼梯质检（级数/宽度/步高/连续性）、楼层对应、楼层高度锁定 | 在线 stair ROI 统计（`laser_mapping.h:960-970`）、`floor_anchor` 状态、`validate_and_gate` |
| 语义可信 | patch 草稿自动门结果 + 放行状态 | 同 §4.13（自动几何门 + 放行策略） |

**机制（三层）**：

1. **增量粗格统计（每批）**：维护 1m 粗格统计（地面点数/观察帧数/z 方差），每批落盘时更新 → 覆盖率/缺口率/稀疏区
2. **事件质检（爬完楼梯）**：生成 patch 草稿的同时输出 `validate_and_gate` 结论 → "合格（建议复核）/ 警告 / 不合格（建议补爬/补扫）"
3. **状态汇总（每 N 帧）**：漂移/闭环/地面有效率/楼层锚定汇总为"绿黄红 + 警告列表"

**输出**（建图可用性面板，走 web 状态字段或新话题，前端建图界面直接显示）：

```json
{
  "readiness": {"localization": "green", "navigation": "yellow",
                "cross_floor": "red", "semantic": "yellow"},
  "warnings": ["B 区地面缺口 12%", "楼梯 A：t04 宽度 0.16m，建议补爬", "闭环未形成"]
}
```

**与 finalize/reviewed 的关系**：在线评估 = **预警/建议**；finalize 权威重算 = 最终结论；两者共用同一套判据代码（C++ 化），保证"在线判不合格的，保存后不会突然变合格"。

**落地**：P3 爬升事件质检（收益最直接，现场当场发现楼梯问题）→ P4 增量粗格统计与面板 → P5 readiness 汇总并与 finalize 结论对齐验收。

## 6. 线程与并发

| 动作 | 线程 | 同步 |
|---|---|---|
| 容器 push_back / 滑窗释放 | Run() 主线程 | `mtx` |
| 入队快照（取 shared_ptr / 位姿） | Run() 主线程 | `mtx` |
| pcd 写盘、fsync | 写线程 | 无锁（只读不可变对象 + 自有队列） |
| 位姿文件重写 | 写线程（读主线程快照） | 位姿快照入队时复制 |
| 索引/游标写 | 写线程 | 只由写线程写 |
| 闭环修改位姿 | GTSAM/主线程 | 置 `pose_dirty` + 递增 `pose_version`，由写线程下轮重写 |
| Provider 读盘 | 调用线程（loop/handoff） | `mtx` 保护容器 + LRU 互斥 |

**约束**：读盘回退（Provider）不得引入长阻塞；P2 先做同步读 + 容量上限，实测不足再异步化。

## 8. 分阶段实施步骤（详细设计）

### 8.1 总览：依赖、并行与开关

```
P0 写路径+最终化 ──► P1 ground/obs 释放 ──► P2 surf 滑窗+Provider ──┐
   （地基，必须先做）                                            │
P3 语义草稿（C++）── 可与 P1/P2 并行 ─────────────────────────────┴──► P4 产物烘焙 ──► P5 恢复+resume
```

- **每阶段独立开关、可单独回退、默认关**；开关关闭时行为与现状完全一致
- 每阶段有明确"验收闸门"，闸门不过不进入下一阶段
- 工程纪律：每个阶段先出"回归包"（同一 bag 对比老流程），再做增量

**目标**：建图中"随产随写"、断电可恢复、保存产物与旧流程逐文件等价。**本阶段只写不释放**，验证写入正确性。

### 8.3 P1：ground/obs 释放（约 37% 收益、几乎零风险）

**目标**：窗口外的已落盘 ground/obs 从内存释放；finalize 改为**从磁盘流式读**（不再依赖内存容器）。

### 8.8 P6：专用显示地图发布器（2026-10-22）

**背景**：P1/P2 开启 `realtime_store_release_surf` / `on_demand_load_enable` 后，`global_map/global_ground` 依赖 `show_globalmap_flag` + `DisplayAccumCatchupAndPublish` 的增量路径；实测该路径在 mapping 模式下会为空，前端只剩红色 `current_pointcloud`。把释放/按需加载关掉三色恢复，但大图内存会持续增长，不能作为生产方案。

**目标**：保留 P1/P2 的释放/按需加载能力，同时独立维护一份低分辨率显示地图，稳定发布三色点云。显示地图不参与建图、匹配、回环和保存。

#### 8.8.1 架构

```text
首关键帧前（live fallback）               首关键帧后（P6 正式显示）
当前 map 系 surf / current ground          关键帧容器/Provider/磁盘
        │                                            │
        ▼                                            ▼
live_display_map_ / live_ground_           display_map_thread（0.5Hz）
  体素累积 → publish                         新关键帧游标 + Provider 回读
        │                                            │
        └──────────────► /x_nav/global_map ◄─────────┘
                         /x_nav/global_ground
```

- **首关键帧前**：没有关键帧，display_map_thread 无法构建；live fallback 代码保留但现场禁用，避免首帧姿态未稳定造成倾斜。
- **首关键帧后**：P6 正式显示地图发布；两者都只影响发布，不影响匹配/存储。

#### 8.8.2 关键设计

1. **与存储释放解耦**：显示线程只消费关键帧和 Provider，不受 `realtime_store_release_surf_` 影响；原始帧释放后由 Provider/磁盘回读。
2. **增量游标**：`display_map_cursor_` 记录已消费的绝对关键帧号；新帧只追增量，不全量重建。
3. **显示地图降采样**：surf/ground 各自体素累积，默认 `0.3m`；点数超过 `global_map_display_max_points` 时自动放大体素，避免内存失控。
4. **位姿修正**：闭环/地图重载/清空时置 `display_map_dirty_`，下一轮清空显示地图并从 0 重建；重建在独立线程，不阻塞匹配。
5. **按订阅者发布**：没有 `global_map/global_ground` 订阅者时跳过构建/发布；有订阅者再追进度。
6. **首关键帧 live fallback（当前禁用）**：代码保留 `updateLiveDisplayMap/updateLiveDisplayGround`，但首帧姿态未稳定时会发布倾斜点云，现场默认不调用；交给首关键帧 + P6 显示。
7. **首帧稳定性处理**：首关键帧正常记录，但显示地图跳过首个 mapping 关键帧，从第二个关键帧开始发布，避免首帧初始姿态尚未稳定导致绿色/蓝色倾斜。
   - IMU warmup 使用 `imu_init_num=200`（50/100 在部分启动姿态下仍会出现明显首帧俯仰）；live fallback 禁用。
8. **legacy 回退**：`global_map_display_mode=legacy` 时线程不启动，回到原 `visualizeGlobalmap` 路径；`off` 时完全不发布全局图。

### 11.3 待拍板问题（按"为什么定不了"分类拆解）

> 这些问题不是"卡住"，而是**现在拍板=拍脑袋**。按原因分四类：
> - **A 等实测**：拿机器人/数据跑一次就能定（先用默认值开工）
> - **B 等勘察/评审**：代码结构或团队取舍，扫一遍代码 / 开一次评审后定
> - **C 权衡验证**：先用最简版跑，让数据说话
> - **D 评审确认**：设计细节，过一遍评审即可
>
> 每条格式：**问题 → 为什么现在定不了 → 怎么定（拍板条件）→ 当前默认值**

#### A 类：等实测（数据说话）

> **实测记录（2026-10-10，robot-3011）**：Intel x86 14 核 / 11GB RAM（可用 8.5GB）/ 30GB swap；存储为 **NVMe SSD**（Fanxiang S500Pro 256GB，ext4，已用 86% 剩 28GB）——**不是 eMMC**；PCL 1.10 实测 `sizeof(PointXYZI)=32B`、`sizeof(PointXYZINormal)=48B`。

**A1. 滑窗参数（帧数/半径）与 LRU 缓存上限的起步值**（原 #2）—— ✅ **已实测定型（起步值）**
- 实测（cf09301，170 帧）：单帧内存 = surf 4109点×48B + ground 311×32B + obs 3263×32B ≈ **0.31MB/帧**
- 推算：1000 帧 ≈ 311MB；3000 帧 ≈ 0.93GB；10000 帧 ≈ 3.1GB（机器人可用内存 8.5GB）
- 结论：`window_frames=200`（≈62MB，无压力）、`window_radius=15m`（P1 ground/obs 激进释放，便于验证；P2 surf 建议 ≥30m）、`cache_mb=1024`（≈可缓存 3300 帧，比 cf09301 全图多 3 倍）均安全，保持默认
- 保留动作：高密度激光/大图（每帧 2~5 倍点）时复测一次

**A2. flush 间隔 / fsync 批量 / 限速的最终值**（原 #3）—— ✅ **基本定型（硬件是 NVMe 而非 eMMC，风险大降）**
- 实测写入：顺序大块 850~1367 MB/s；小文件（200KB×300，batch fsync=20）整体 **129MB/s**，单帧写入 p50=**0.23ms**，每批 20 帧 fsync 一次约 **24ms**（在后台线程，无感）
- 结论：`flush_interval=20`、`fsync_batch=20` 可行且余量巨大；**限速从 20MB/s 上调为 150MB/s**（或仅监控不限速）；写盘对 SLAM 帧处理的增量可忽略
- 遗留（转入风险表）：磁盘**已用 86%（剩 28GB）**——容量水位管理、已归档块清理策略需要在实施时定

**A3. Provider 读盘是否首版就异步**（原 #4）—— ✅ **定型：首版同步**
- 实测（cf09301 surf 逐帧冷读）：p50=**0.39ms**、p95=0.59ms、max=2.25ms；热读 0.05ms；全量 170 帧冷读仅 **72ms**

### 11.4 建图期回环检测保障（含大回环）

> **问题**：主题一把窗口外的关键帧点云释放了，而回环检测（尤其大回环）需要"历史环境"——这个能力怎么保持？
> **结论一句话**：**回环需要的"索引"常驻（位姿 + 描述子），"素材"按需读盘（Provider），"正在用"的帧靠 shared_ptr 引用计数保护**——释放只影响内存占用，不影响回环。

#### 11.4.1 先拆开：回环到底需要什么

| 环节 | 需要什么 | 体量 | 主题一处置 |
|---|---|---|---|
| 短程候选 | 位姿 KD 树（3m 半径找历史帧） | K 级（小） | **常驻**，不进滑窗 |
| 大回环候选 | 描述子检索（不依赖位姿距离） | ring key 80B/帧；完整描述子 4.8KB/帧 | **常驻/按需**，见 11.4.2 |
| 候选验证 | 历史帧点云拼子图（当前/历史各 ~10 帧） | 13 万点/帧 ≈ 0.13MB/帧 | **Provider 按需读盘** |
| 全局优化 | GTSAM 因子图 + 历史位姿 | K 级（小） | **常驻**（现有） |

**只有"历史帧点云"是大件**——恰好就是滑窗要释放的东西；其余都小，全部常驻。

#### 11.4.2 三条保障机制

1. **索引常驻**
   - 位姿 KD 树：一直常驻（不随滑窗释放）——短程回环照旧
   - 描述子：**建图中随关键帧增量计算**（SC 0.9ms/帧，实测；新增开关 `realtime_descriptor_enable`）；**body 系计算，闭环改位姿不会让它失效，不用重算**（主题五关键洞察）
   - 存储策略（按规模分档）：ring key 全量常驻（80B/帧，10 万帧 ≈ 8MB）；完整描述子建议**量化存储**（float32→uint8 后 10 万帧 ≈ 120MB，也可按需从磁盘读）
2. **点云按需读取（Provider）**
   - 历史子图由 Provider 从磁盘读：单帧冷读 **p50=0.39ms**、170 帧全读 72ms（§11.3 A3 实测）→ 验证一次大回环只需读 ~10 帧（1~3MB），毫秒级完成
   - **连锁安全**：Provider 返回 `shared_ptr`——只要回环还在用这张子图，**引用计数 >0，滑窗释放只是"移出容器"，内存不会真正释放**；用完自动回收，无需额外保护标记
3. **时机与降级**
   - 检测在 `loopClosureThread`（1Hz，现有）；优化在 `gtsam_optimization` 主流水线（现有）→ 与主题一无冲突
   - 读盘失败/超时 → **跳过本轮**，不影响建图与跟踪；退化用现有 3m 短程回环
   - 闭环后：局部 IVox 按 Spec 全量重建（唯一硬例外）；语义草稿/派生图标脏；建图中没有瓦片（finalize 才生成），无需重烘焙

#### 11.4.3 大回环专项（与主题六 §7.3 对应）

```
① 候选生成：描述子检索（不碰点云、不受位姿半径限制）
② 验证：Provider 读候选邻域子图 → ICP
③ 防误检：多帧一致性（连续 3~5 帧）+ 描述子/fitness 双门槛 + 楼层约束
④ 通过：写回环因子 → GTSAM 全局修正 → 位姿重写（pose_version++）→ 局部 IVox 重建
```

- **跨图（inter-map）**：现有机制直接从"对图目录"读文件，天然不依赖本图内存，完全兼容
- **描述子跨闭环不变**：位姿修正只改"点云摆在哪"，不改 body 系指纹 → 大回环索引永不过期
- **算力**：描述子增量 0.9ms/帧 + 检索只在触发时限流执行（1Hz 线程内），不挤占跟踪

#### 11.4.4 边界与注意事项

- 匹配窗口（10m IVox + 5m 邻域）的"永不释放"是**连续跟踪**需求，与回环无关——两者互不干扰
- 回环优化与写线程的位姿竞争：沿用 `pose_version` + `pose_dirty` 机制（§4.7）
- 描述子常驻的量化方案待定（float32 vs uint8；建议量化 or "ring key 常驻 + 完整描述子按需"）
- 建图中描述子必须**在线计算**（finalize 预计算只能服务定位/离线）；成本 0.9ms/帧，归入语义流水线

#### 11.4.5 一句话

**滑窗释放的是"点云素材"；回环靠"常驻索引（位姿+描述子）+ 按需读盘 + 引用计数"，所以短程回环照旧、大回环（描述子检索）不受影响；唯一新增是"建图中在线算描述子"这项轻量开销（0.9ms/帧）。**
